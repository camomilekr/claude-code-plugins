# resolve-coderabbit-review 스킬 토큰 비용 벤치마크

## 요약

resolve-coderabbit-review 스킬의 Subagent 처리 방식을 **코멘트 단위 → 파일 단위 (그룹 코멘트 수 ≥ 2일 때만 그룹핑)** 으로 변경하여, 실 사용 패턴(라운드 단위 호출) 기준 토큰 사용량을 **22.3% 절약**했다 (최근 1,000 PR 합산 기준).

- **손해 PR 0건** — 그룹 코멘트 수 = 1인 경우 단일 코멘트 프롬프트로 폴백하여 오버헤드 제거
- 큰 PR에서 효과 큼: 절약 토큰 최대 **+87,065 (PR #5743, 60.1%)**, 절약률 최대 **+71.4% (PR #6453)**
- 분석 정확도에는 영향 없음 — 줄인 것은 같은 파일의 "중복 Read"이지, 코드 컨텍스트 자체는 양쪽 동일

### 측정 진화

| 측정 | 가정 | 결과 |
|------|------|------|
| 1차 (15 PR, 누적 기준) | PR 전체 코멘트를 1회 호출 | +35.3% 절약 (과대평가) |
| 2차 (15 PR, 라운드 기준) | 5분 윈도우 라운드 분리, 모든 파일 그룹핑 | +21.5% 절약, 일부 PR 손해 |
| 3차 (200 PR, 라운드 + 분기) | 라운드 분리 + N=1 단일 / N≥2 그룹 분기 | +17.4% 절약, 손해 0 |
| **4차 (1,000 PR, 라운드 + 분기)** | 모집단 5배 확장 | **+22.3% 절약, 손해 0** |

> 1,000 PR로 모집단을 확장하니 효과가 더 명확해졌다. CodeRabbit 코멘트가 있는 PR은 356개(35.6%)로 200 PR 때(28.0%)보다 비율이 안정화됐고, 절약 PR 139개와 손해 PR 217개의 합산이 net +1,265,900 토큰(+20.8%)이며, 분기 로직 적용 시 +1,356,465 토큰(+22.3%)으로 추가 향상됐다.

## 1. 배경

### resolve-coderabbit-review 스킬이란

PR에 달린 CodeRabbit 리뷰 코멘트를 자동으로 분석하고, 적절성을 판단하는 스킬이다. 각 코멘트에 대해 해당 파일의 코드를 읽고 지적 내용과 비교한 뒤, 수정이 필요한지 아니면 반박 응답이 필요한지를 분류한다.

### 문제: 코멘트마다 Subagent를 생성하면 같은 파일을 반복해서 읽는다

구버전은 코멘트 1개당 Subagent 1개를 생성했다. 같은 파일에 코멘트가 4개 달리면, 4개의 Subagent가 **동일한 파일을 각각 한 번씩** 읽었다. 이는 불필요한 토큰 낭비다.

### 해결: 같은 파일의 코멘트를 묶어 한 번만 읽기

신버전은 **파일 단위로 코멘트를 그룹핑**하여 Subagent를 생성한다. 같은 파일에 코멘트가 4개 있으면, 1개의 Subagent가 파일을 1회 읽고 4개 코멘트를 모두 분석한다.

| | 구버전 | 신버전 |
|---|---|---|
| Subagent 단위 | 코멘트 1개 = 1 Subagent | **파일 1개 = 1 Subagent** |
| 파일 Read | Subagent마다 독립적으로 Read | **파일당 1회만 Read** |
| 병렬 진입 분기 | 코멘트 수 > 5 → 병렬 | 고유 파일 수 > 3 → 병렬 |
| 프롬프트 형식 분기 | 없음 (모두 단일 코멘트 형식) | **N=1 → 단일 코멘트 / N≥2 → 파일 그룹** |

> **두 가지 분기**가 있다. 첫 번째(병렬 진입)는 메인 에이전트가 직접 처리할지 Subagent를 띄울지 결정하는 분기, 두 번째(프롬프트 형식)는 파일별 그룹의 코멘트 수에 따라 단일 코멘트 프롬프트와 파일 그룹 프롬프트 중 어느 것을 쓸지 결정하는 분기다. 후자는 4장에서 1,000 PR 검증으로 도입됐다.

> 분석 정확도에는 영향이 없다. 줄인 것은 "같은 파일의 중복 Read"이지 "파일을 읽지 않는 것"이 아니므로, 각 코멘트가 참조하는 코드 컨텍스트는 양쪽 동일하다.

## 2. 측정 방법

### 라운드 단위 측정 — 실 사용 패턴 반영

CodeRabbit 리뷰는 PR 생애에 걸쳐 여러 번 게시된다:

```
[push] → CodeRabbit 리뷰 라운드 1 → /resolve-coderabbit-review 호출
       → 사용자 fix 커밋
[push] → CodeRabbit 리뷰 라운드 2 → /resolve-coderabbit-review 호출
       → ...
```

따라서 PR에 누적된 모든 코멘트를 한 번에 처리한다고 가정하면 라운드 간 분산 효과가 무시되어 절약률이 과대평가된다. 본 측정은 코멘트의 `createdAt` 타임스탬프를 기준으로 **5분 윈도우 클러스터링**으로 라운드를 분리하고, 각 라운드를 독립된 스킬 호출로 시뮬레이션한 뒤 합산한다.

> 같은 CodeRabbit 리뷰 제출의 코멘트는 1~2초 내에 일괄 게시되고, 라운드 간 갭은 보통 10분 이상이라 5분 윈도우면 안전하게 분리된다.

### 비교 대상: 실측 가능한 가변 토큰만 비교

| 항목 | 포함 여부 | 이유 |
|------|----------|------|
| Subagent 프롬프트 토큰 | **포함** | 실제 프롬프트를 구성하여 토크나이저로 측정 |
| 파일 Read 토큰 | **포함** | 실제 파일 내용을 읽어 토크나이저로 측정 |
| Subagent 고정 오버헤드 | 제외 | 시스템 프롬프트 + 도구 스키마의 정확한 크기를 알 수 없음 |
| 출력 토큰 | 제외 | 양쪽 동일 구조 (코멘트당 분석 결과), 차이 없음 |
| 메인 에이전트 비용 | 제외 | 양쪽 동일 (코멘트 조회, 분기 판단, 최종 보고) |

### 측정 도구

- 토크나이저: `tiktoken` cl100k_base (GPT-4용). Claude 토크나이저와 ~5-10% 차이가 있으나, 동일 토크나이저를 양쪽에 적용하므로 **상대 비교에는 영향 없음**
- 스크립트: `scripts/measure_multi.py`
- 데이터: `gh api graphql`로 PR의 CodeRabbit 코멘트(bot 코멘트만) + `createdAt` 수집. 측정용으로 `INCLUDE_RESOLVED=1` 환경변수를 통해 resolved 처리된 코멘트도 포함

### 측정 절차

1. `gh api graphql`로 PR의 CodeRabbit 코멘트와 `createdAt` 수집 (resolved 포함)
2. `createdAt` 기준 5분 윈도우 클러스터링으로 라운드 분리
3. 각 라운드에 대해:
   - **구버전 시뮬레이션**: 코멘트 1개당 프롬프트 + 해당 파일 Read 토큰 합산
   - **신버전 시뮬레이션**: 파일별 코멘트 그룹핑 후 프롬프트 + 파일당 1회 Read 토큰 합산
4. PR 단위로 라운드 합계 비교

### 테스트 대상

코멘트 규모별로 3개 그룹, 각 5개 PR (총 15개). 코멘트 수는 측정 시점 기준이며, 일부는 outdated 처리되어 첫 측정 대비 줄었을 수 있다.

### 신버전 프롬프트 오버헤드와 음수 절약률

라운드 집중도가 1.0(전부 다른 파일)인 케이스에서 신버전이 -2~-3% 손해를 보는 이유는, 같은 파일이 1개만 있어도 신버전 프롬프트는 JSON 배열 형식과 추가 지침 텍스트를 포함하기 때문이다. 파일 1개당 코멘트가 1개뿐이면 그룹핑 이득은 없고 프롬프트 오버헤드만 남는다.

**손익 분기점**: 라운드 집중도 1.05~1.1 부근. 이보다 낮으면 의미 없거나 손해, 이보다 높으면 절약 시작.

## 4. 1,000 PR 모집단 검증 — 분기 로직 도입

15 PR → 200 PR → 1,000 PR로 단계적으로 확장하며 검증했다. 200 PR 단계에서 라운드 집중도 1.0 케이스(파일에 코멘트가 1개뿐인 그룹)가 84%에 달하는 것을 확인하고 분기 로직을 설계했으며, 1,000 PR로 모집단을 확장해 효과와 안정성을 재확인했다.

### 1,000 PR 분포

| 지표 | 결과 |
|------|------|
| 전체 PR | 1,000 |
| CodeRabbit 코멘트 있는 PR | 356 (35.6%) |
| 그 중 절약 PR | 139 (39.0%) |
| 그 중 **손해 PR** | **217 (61.0%)** |
| 356 PR 합산 절약 (분기 X) | +1,265,900 토큰 (+20.8%) |

**빈도로는 손해가 더 흔하지만, 토큰량은 절약이 압도**:
- 절약 PR 평균: **+9,384 토큰 (+26.6%)**
- 손해 PR 평균: −177 토큰 (−4.4%)
- 차이 약 53배 → 큰 PR 1건의 절약이 작은 PR 수십 건의 손해를 메움

### 파일당 코멘트 분포 (1,000 PR · 모든 라운드 · 1,610개 파일-그룹 케이스)

|---|---|---|---|
| 1개 | 1,297 | **80.6%** ← 손해 발생 | 80.6% |

**대부분(81%)의 파일-코멘트 그룹은 1개씩만 달린다.** 이 케이스에서 신버전 그룹 프롬프트의 JSON 배열 + 추가 지침 텍스트가 평균 -68토큰 손해를 발생시키고, 작은 PR이 모두 이 케이스로만 구성되면 PR 단위 손해가 누적된다.

### 분기 로직 적용 시뮬레이션

같은 파일에 코멘트가 1개뿐인 그룹은 단일 코멘트 프롬프트(구버전 형식)로 폴백:

```
파일별 그룹핑 → 그룹 코멘트 수에 따라 분기
  N == 1 → 단일 코멘트 프롬프트 (구버전과 동일)
  N >= 2 → 파일 그룹 프롬프트 (그룹핑 효과 발생)
```

#### 효과 (356개 PR 합산)

| | 구버전 | 신버전 (분기 X) | **신버전 (분기 O)** |
|---|---|---|---|
| 합산 토큰 | 6,079,351 | 4,813,451 | **4,722,886** |
| 절약 | 기준 | +1,265,900 (+20.8%) | **+1,356,465 (+22.3%)** |
| 절약 PR | - | 139 | **148** |
| 손해 PR | - | 217 | **0** |
| 변동 없음 | - | 0 | 208 |

**손해가 정확히 0**이 되고, 추가로 +90,565 토큰 절약(7% 증가).

> 변동 없음 208개 PR은 모든 파일 그룹이 N=1로 구성된 작은 PR로, 분기 로직에 의해 구버전과 동일하게 처리된다.

| 한 파일에 코멘트 N개 | 케이스 수 | 평균 절약 토큰 |
|---|---|---|
| 1개 | 1,297 | -68 (분기 적용 시 0) |
| 2개 | 247 | **+2,500 추정** |
| 3개 | 48 | **+5,000 추정** |
| 4개 | 15 | **+7,500 추정** |
| 5개+ | 3 | **+10,000+ 추정** |

> N≥2 케이스 평균은 200 PR 측정에서 산출한 값(N=2: +2,483, N=3: +4,843, N=4: +9,370)을 기반으로 한 근사. 1,000 PR 합산 결과는 이를 잘 반영한다.

**한 파일에 코멘트 1개 추가될 때마다 약 2,000-2,500토큰씩 절약 증가** — 파일을 한 번 더 읽지 않게 된 비용에 해당.

## 5. 측정의 한계

- **라운드 윈도우는 휴리스틱**: 5분 윈도우는 본 측정 데이터셋에서 안전하게 라운드를 분리했지만, CodeRabbit이 매우 큰 PR을 분할해서 5분 이상 걸쳐 게시하는 경우가 있다면 한 라운드를 두 라운드로 잘못 분리할 수 있다. 다만 이 경우 절약률을 **과소평가**하므로 보수적이다.
- **코멘트 데이터의 시점 의존성**: GraphQL `reviewThreads`는 outdated/resolved 상태에 따라 일부 코멘트를 누락할 수 있다. 본 측정은 `INCLUDE_RESOLVED=1`로 resolved까지 포함했으나, 강제 푸시 등으로 outdated 처리된 코멘트는 여전히 빠질 수 있다. 첫 측정 대비 일부 PR의 코멘트 수가 줄어든 이유다.
- **고정 오버헤드 제외**: Subagent 1개당 시스템 프롬프트 + 도구 스키마의 고정 오버헤드(~2K tokens 추정)는 측정에 포함되지 않았다. 이를 포함하면 신버전(분기 O)이 Subagent 수를 줄이는 효과로 추가 절약이 더해진다.

### 고정 오버헤드 포함 시 추정 (1,000 PR · 분기 O 기준)

| 항목 | 수치 |
|------|------|
| Subagent 합계 (356 PR) | 구버전 2,011개 → 분기 O 1,610개 (**401개 감소**) |
| Subagent 평균 (코멘트 있는 PR당) | 5.6개 → 4.5개 (PR당 1.1개 감소) |
| 고정 오버헤드 절감 추정 | 1.1 × 2,000 = **~2,253 tokens/PR** |
| 가변 토큰 절약 (실측, 분기 O) | **3,810 tokens/PR** (1,356,465 / 356) |
| PR 평균 합산 추정 | **~6,063 tokens/PR** |
| **356 PR 합산 추정** | **~2,158,465 tokens** (가변 1,356,465 + 고정 802,000) |

> 고정 오버헤드 ~2K tokens는 보수적 추정치다. Claude Code의 실제 시스템 프롬프트 + 도구 스키마는 더 클 수 있어, 실제 절감은 위 수치보다 클 가능성이 높다.

### 재측정 방법

`measure_multi.py`는 내부적으로 `INCLUDE_RESOLVED=1`을 설정해 resolved 코멘트도 historical data로 포함시킨다 (실 사용 시에는 unresolved만 처리).

```bash
# 가상환경에 tiktoken 설치
pip install tiktoken

# 1. 15 PR 측정 (3장 결과 재현)
python3 plugins/code-review/skills/resolve-coderabbit-review/scripts/measure_multi.py \
  6569 6527 6483 6453 6433 6490 6486 5810 6455 6493 \
  6020 6425 6283 6472 6454

# 2. 1,000 PR 측정 (4장 결과 재현)
gh pr list -L 1000 --state all --json number --jq '.[].number' > pr_list.txt
python3 plugins/code-review/skills/resolve-coderabbit-review/scripts/measure_multi.py --file pr_list.txt -o results.json

# 3. 윈도우 변경 시 -w 옵션 (단위: 초)
python3 plugins/code-review/skills/resolve-coderabbit-review/scripts/measure_multi.py 6020 -w 600
```

> **시점 의존성**: `gh api graphql`로 가져오는 코멘트는 측정 시점의 `outdated`/`resolved` 상태에 따라 달라진다. 첫 측정 이후 강제 푸시로 outdated 처리된 코멘트는 누락될 수 있어, 재측정 시 동일한 절약 토큰 수치를 정확히 재현하지 못할 수 있다. 절약률(%)은 모집단 변동에 비교적 안정적이다.
