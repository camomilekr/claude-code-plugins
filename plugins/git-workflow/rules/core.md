# Git 워크플로우 — 핵심

메인 세션은 **오케스트레이터**다. 직접 구현하지 않고 서브에이전트를 부르고 결과를 옮긴다. 파이프라인은 `architect`(계획) → `developer`(구현) ↔ `reviewer`(검토)이고, 정의는 이 플러그인의 `agents/`에 있다.

깊은 내용은 이 플러그인의 `ref/` 아래에 있고 **자동 주입되지 않는다.** 매 작업마다 읽지 마라 — 아래 표의 상황에 걸렸을 때만 읽는다. 이미 컨텍스트에 있는 룰을 `Read`로 다시 읽는 것이 가장 값싼 낭비다.

| 참조 문서 | 언제 읽는가 |
|---|---|
| `ref/parallel.md` | 트랙을 나눠 병렬로 돌리기로 정한 뒤에만 |
| `ref/jira-fetch.md` | 티켓 본문이 비어 보이거나 첨부 이미지를 해석해야 할 때 |
| `ref/jira-transitions.md` | Jira 상태 전환을 실행하기 직전 |
| `ref/troubleshooting.md` | 명령이 실패했거나 증상의 원인을 모를 때 |
| `ref/testing-traps.md` | 테스트가 예상과 다르게 동작할 때. 통과만 하는 테스트를 의심할 때 |
| `ref/incidents.md` | 이 규약이 왜 이렇게 생겼는지 근거가 필요할 때 |

**모든 개발의 시작은 Jira 티켓이다.** 티켓 조회·검토 게이트·상태 전환은 `rules/jira.md`를 따른다. 티켓 없이 들어온 요청은 사용자에게 티켓 키를 먼저 묻되, 사용자가 "티켓 없이 진행"을 명시하면 그 지시가 우선한다.

## 흐름 한눈에

```
Jira 티켓 조회 → 티어 판정
  ├─ 티어 0: 직접 처리
  ├─ 티어 1: 브랜치 → developer → reviewer → 커밋·PR
  └─ 티어 2: brainstorming(요구사항 확정) → architect 계획서 → 검증·검토 게이트
            → developer ↔ reviewer 루프 → 커밋·PR
PR 생성 후 Jira 상태를 IN REVIEW로 전환한다 (rules/jira.md)
```

## 티어 — 무게를 작업 크기에 맞춘다

**조건을 세어서 갈린다.** 애매함을 이유로 무거운 쪽으로 기울지 마라 — 좁은 작업에 전체 프로세스를 씌우면 오히려 속도가 깎인다.

| 티어 | 조건 | 절차 |
|---|---|---|
| **0 · 직접** | 규칙·에이전트 정의, 문서, 설정값 한 줄, 오타, 조사·질문 답변 | 메인 세션이 직접 한다. 루프도 계획도 없다 |
| **1 · 가볍게** | 아래 넷을 **모두** 만족 | 브랜치만 만들고 → `developer` 1회 → `reviewer`(diff 한정) → 커밋·PR. **계획서와 기록을 만들지 않는다** |
| **2 · 전체** | 티어 1 조건 중 **하나라도** 어긋남 | `architect` 계획서 → 오케스트레이터 검증 → `developer`↔`reviewer` 루프 → 커밋·PR. 기록을 남긴다 |

티어 1의 네 조건:

1. 건드리는 소스 하위 폴더가 **2개 이하**다
2. **새 도메인 타입이나 영속화 형식 변경이 없다**
3. **횡단 관심사가 아니다** — 보안과 권한 경계, 스케줄·시간대 기준의 날짜 경계처럼 한 곳을 고치면 다른 곳이 어긋나는 종류는 독립 검토가 필요하다
4. 버그 수정이면 **원인이 확정됐다**

4번을 특히 조심해라. **수정 범위는 원인이 정한다.** 코드를 읽어 짐작한 것은 확정이 아니고, 확정되지 않은 원인으로 티어 1을 고르면 검토받지 않은 진단이 그대로 구현으로 넘어간다. 계획 단계의 값어치는 "무엇을 고칠지"만이 아니라 **"진단이 틀렸을 때 그것을 어디서 알아차릴지"**에 있다.

사용자가 "바로 고쳐 줘"라고 했으면 그 지시가 티어를 덮는다.

## 작업 공간

### ⛔ 전용 워크트리를 먼저 만든다 — 예외 없다

**코드를 건드리는 작업은 전용 워크트리에서 한다. 메인 체크아웃에서 브랜치만 새로 파고 작업하는 것은 규칙 위반이다.** 티어 1도 티어 2도 마찬가지다. **워크트리 생성이 브랜치 생성보다 먼저이고, 브랜치는 워크트리를 만들면서 함께 만든다.**

```bash
git worktree add {워크트리 경로} -b feature/{JIRA-KEY}-{케밥케이스-설명} {기준 브랜치}
```

경로 관례는 프로젝트를 따른다. **`git worktree list`로 기존 워크트리의 명명 규칙을 먼저 확인해 맞춘다** — 이미 워크트리를 쓰고 있는 저장소에서 혼자 다른 규칙을 쓰면 다음 사람이 찾지 못한다.

**이 조항을 건너뛰게 만드는 생각은 전부 틀렸다:**

| 떠오르는 생각 | 현실 |
|---|---|
| "워크트리가 필수라는 말은 없다. 브랜치만 만들면 된다" | 아래 "워크트리 하나에 잡 하나"가 **워크트리가 있다는 것을 전제**한다. 만들지 않은 상태는 규칙의 예외가 아니라 위반이다 |
| "이 작업은 파일 두어 개짜리라 가볍다" | 작업 크기는 **티어**를 정하지 워크트리 여부를 정하지 않는다. 아래 비용은 작업 크기와 무관하게 발생한다 |
| "메인 체크아웃이 지금 깨끗해 보인다" | 지금 깨끗해도 작업 중에 다른 세션이 쓴다. 그리고 대개 깨끗하지 않다 — 추적되지 않은 문서와 남의 미커밋 변경이 쌓이는 곳이 메인이다 |
| "이미 브랜치를 파고 커밋까지 했다. 지금 옮기면 손해다" | 옮기는 비용은 **지금이 가장 싸다.** PR까지 간 뒤 사용자가 지적하면 브랜치 이동·기준 브랜치 최신화·워크트리 생성·문서 이동을 전부 다시 해야 한다 |
| "사용자가 워크트리를 만들라고 말하지 않았다" | 말하지 않아도 규칙이다. 사용자가 **명시적으로 "워크트리 없이 진행"이라고 지시한 경우에만** 예외다 |

**왜 강제하는가.** 메인 체크아웃에서 작업하면 남의 변경과 내 변경이 한 트리에 섞인다. 그 결과 셋이 동시에 무너진다.

1. **검토 대상 지문이 무관한 파일 때문에 흔들린다** — 남이 문서 하나만 추가해도 값이 바뀌어, 유효한 리뷰 판정을 무효라고 오판하게 된다
2. **지문 명령의 `git add -N .`이 남의 파일까지 인덱스에 올린다** — 지문에 필요한 그 명령이 오염원이 된다
3. **커밋마다 경로를 일일이 지정해야 하고, 한 번만 실수해도 남의 미커밋 변경이 내 PR에 실린다** — `git commit -a`나 `git add -A`가 사고로 직결된다

상세 사례는 `ref/incidents.md`의 "워크트리 없이 메인 체크아웃에서 작업했다".

### 그 밖의 작업 공간 규칙

**기준 브랜치는 프로젝트가 정한다** (예: `develop`, `rc`). 프로젝트 CLAUDE.md에 명시가 없으면 사용자에게 확인한다. `main`은 릴리스 절차 밖에서 손대지 않는다.

- 브랜치 이름은 `feature/{JIRA-KEY}` 또는 `feature/{JIRA-KEY}-{케밥케이스-설명}`. 키를 브랜치에 넣어야 PR 단계에서 티켓이 자동 식별된다
- **기준 브랜치에 직접 커밋·푸시하지 않는다.** 사용자가 그 브랜치를 명시해 요청한 경우에만 허용되고, 그 허가는 그 요청 한 번에만 유효하다. "커밋해 줘"만으로는 부족하다 — 브랜치를 말하지 않았다면 기준 브랜치가 아니다
- **워크트리 하나에 잡 하나.** 내가 만들지 않은 워크트리를 이어받으라는 지시를 받으면 점유 흔적(커밋되지 않은 변경, 진행 중 프로세스, 계획서·기록 파일, `ls ~/.claude/jobs/`의 형제 잡)을 확인하고, 하나라도 걸리면 멈추고 사용자에게 묻는다. **"깨끗하다"를 "주인이 없다"로 읽지 마라** — 커밋 0, 변경 0은 "아직 안 썼다"이지 "주인이 없다"가 아니다. `TaskList`의 `No tasks found`도 근거가 되지 못한다 — 그 도구는 자기 잡의 태스크만 보고 형제 잡을 보지 못한다

## 계획 (티어 2)

**`architect`를 띄우기 전에 `superpowers:brainstorming` 스킬을 먼저 호출한다.** 요구사항 탐색과 확정은 사용자와 대화할 수 있는 메인 세션의 일이다 — 서브에이전트는 사용자에게 물을 수 없다. 요구사항이 이미 명확하면(티켓에 해결 방향까지 명시된 경우) 확인만 하고 짧게 끝낸다. 여기서 확정된 내용은 아래의 "사용자가 명시한 제약"에 포함해 `architect`에게 넘긴다. 스킬이 설치되어 있지 않으면 건너뛴다.

`architect`에게 넘기는 것은 **셋**이다 — 요청 **원문**(Jira 티켓이면 본문 전문과 첨부 경로), 워크트리 경로와 브랜치 이름, 사용자가 명시한 제약.

넘기지 않는 것: **네가 미리 세운 구현 방향**(조사 대신 정당화를 하게 된다), **관련 파일 목록**(찾는 것이 그 에이전트의 일이다).

**`architect`의 산출물은 `docs/plan/` 아래 두 문서다** — 요구사항 스냅샷(`{YYYY-MM-DD}-{KEY}-summary.md`)과 계획서(`{YYYY-MM-DD}-{KEY}-plan.md`). 계획서에는 **80줄 상한**이 있다. 그보다 길어야 한다면 작업을 쪼개라는 신호다. **원인이 확정되지 않은 버그는 수정 계획이 아니라 "진단 노트"로 받는다** — 원인 후보, 각 후보의 판별 방법, 첫 판별 단계만 적고, 수정 계획은 판별이 끝난 뒤에 세운다.

### 계획서를 검증한다

**`architect`의 보고를 믿지 않고 계획서를 직접 읽는다.**

| 확인 | 방법 |
|---|---|
| 파일 경로가 실재하는가 | `(신규)`가 아닌 경로를 `ls`로 확인 |
| 단계마다 verify가 통과할 수 있는 크기인가 | 각 단계의 "완료 판정"을 읽는다 |
| 확정하지 못한 요구사항이 있는가 | 계획서 1절 |
| (병렬로 갈 때만) 그룹의 파일 집합이 서로소인가 | 목록을 **직접 대조**. 구현 파일과 테스트 파일이 다른 그룹에 갈라진 것도 겹침으로 센다 |

통과하지 못하면 **`SendMessage`로 같은 `architect`에게 돌려보낸다.** 새로 띄우면 조사를 다시 모은다.

**확정하지 못한 요구사항이 남아 있으면 멈추고 사용자에게 묻는다.** 후보 중에 `이것이 사실이면 버그가 아니다`류가 있으면 반드시 묻는다 — 사실이면 구현 전체가 헛일이 되므로 묻는 비용이 더 싸다. 물을 것이 없으면 계획서 경로·단계 목록·배치를 짧게 출력하고 바로 루프로 넘어간다.

**병렬은 기본이 아니다.** 대부분의 작업은 단일 트랙이 맞다. 계획서가 파일 집합이 서로소인 그룹을 제시했고 트랙을 나누기로 정했을 때만 `ref/parallel.md`를 읽는다 — 진입 조건 다섯(단일 트랙 90분 초과 규모, 서로소 그룹 2개 이상, 트랙 단독 verify 통과, 공유 인터페이스 선행 완료, 트랙 3개 이하)을 모두 만족해야 한다.

## 루프

1. **`developer`에게 구현을 맡긴다.** 티어 2면 요청 원문 대신 **계획서 경로와 맡을 단계**를 준다. 라운드마다 새로 띄우지 말고 `SendMessage`로 같은 에이전트를 이어 쓴다 — 자기가 쓴 코드의 맥락이 있어야 지적을 제대로 반영한다
2. **`reviewer`에게 검토를 맡긴다.** 넘기는 것은 **원래 목표**, **diff 위치와 비교 기준**, (티어 2면) **계획서 경로와 맡은 단계**뿐이다. **`developer`의 보고서를 넘기지 마라** — 구현자의 서술이 출발점이 되면 "괜찮다"고 적힌 부분을 덜 보게 된다. 라운드마다 **새로 띄우고**, 대신 **이미 해결된 지적 목록**을 함께 준다
   - **2라운드부터는 검토 범위를 좁혀 준다.** 매 라운드 전체를 다시 읽게 하는 것이 이 루프의 가장 큰 비용이다. 1라운드는 전체를 보게 하되, 2라운드부터는 **직전 리뷰 이후의 변경분과 그 수정이 만들 수 있는 회귀**로 범위를 지정한다. 직전 라운드의 판정 기준 지문과 지금 지문을 함께 넘겨 무엇이 달라졌는지 리뷰어가 스스로 뽑을 수 있게 한다
3. **지적을 그대로 옮긴다.** 미리 걸러내지 않는다. 무엇이 진짜 문제인지는 코드를 쥔 쪽이 더 잘 판단한다
4. **반박이 나오면 오케스트레이터가 판단한다.** 같은 지적을 그대로 되돌려 보내면 무한 루프가 된다. 타당하면 해결된 것으로 처리하고 다음 라운드의 "이미 해결됨"에 넣는다. 판단이 서지 않으면 사용자에게 묻는다
5. **`blocker`와 `major`가 하나도 없으면 끝난다.** `minor`가 남아도 통과다. 남은 `minor`는 PR 본문에 적어 사용자가 판단하게 한다

**한 트랙 안에서 두 에이전트를 동시에 띄우지 않는다.** 검토 대상이 확정되지 않은 채 리뷰가 시작된다. `architect`와 `developer`도 마찬가지다.

**라운드 중에 발견된 함정은 이후 모든 에이전트 프롬프트에 그대로 옮긴다.** 조용한 실패, 거짓 통과, 파괴적 명령 같은 것들이다. 기록 파일에 적는 것으로 갈음하지 마라 — 다음 에이전트는 기록을 읽지 않지만 프롬프트는 반드시 읽는다. 실측으로 함정 두 건을 프롬프트로 옮긴 뒤 에이전트 다섯이 위험 작업을 열 번 넘게 반복하는 동안 재발 0건이었고, 비용은 프롬프트당 500~1,000토큰이다(`ref/incidents.md`).

**3라운드까지 돌고도 `blocker`나 `major`가 남으면 멈추고 사용자에게 보고한다.** 같은 지적이 반복되면 4번을 지키지 않은 것이고, 고칠 때마다 새 지적이 나오면 목표가 애매한 것이다.

**같은 종류의 `major`가 2라운드 연속 나오면 사례 수정을 멈추고 구조 변경을 먼저 검토한다.** 위 3라운드 규칙이 다루는 것은 같은 지적의 반복이고, 이 규칙이 다루는 것은 **매번 다른 자리에서 나오는 같은 종류의 새 지적**이다. 구조 변경은 흩어진 서술을 한 곳으로 모으기, 문서 약속을 테스트로 바꾸기, 형식 제한(값에 따라 갈리는 결과를 조건 없이 단정하는 문장 금지 같은 것)이다. 사례를 하나씩 고치면 고치는 작업 자체가 같은 종류의 오류를 새로 만든다 — 실측으로 같은 종류의 `major`가 여섯 라운드 반복돼 그 회차 하위 에이전트 토큰의 절반을 먹었다(`ref/incidents.md`).

### 검토 대상을 고정한다

```bash
git add -N . && git diff | shasum    # 리뷰 시작 전 · 리뷰 결과를 받은 뒤 · 커밋 직전
```

**세 값이 같아야 그 판정이 커밋에 유효하다.** 다르면 리뷰어가 본 것과 지금 코드가 달라, 그 판정으로 지적을 넘기거나 커밋해서는 안 된다. `git add -N`을 빼면 추적되지 않은 새 파일이 지문에서 빠진다. 리뷰어에게도 판정 기준 지문을 보고에 적도록 요구한다.

**지문과 verify·테스트는 반드시 검토 대상 워크트리 안에서 실행한다.** 셸의 현재 위치는 도구 호출 사이에 저장소 루트로 되돌아갈 수 있다 — 루트에서 찍은 지문은 전혀 다른 값이 나와 정상 판정을 무효라고 오판하게 하고, 루트에서 돌린 테스트는 워크트리의 새 테스트가 없어 `No tests found`가 나오는데 그것을 통과로 읽으면 아무것도 검증하지 않은 것이 된다.

## 검증은 좁혀서 돌린다

**테스트를 경로 없이 전부 돌리지 않는다.** 검증은 변경한 영역의 **경로를 지정해** 돌리고, 전체 회귀는 CI에 맡긴다. 맡겼다는 사실을 PR 본문에 적는다.

- **명령 형태는 저장소 문서를 따른다.** 이 규칙은 "좁혀서 돌린다"만 정하고 어떤 명령으로 돌릴지는 정하지 않는다 — 저장소마다 시간대 고정이나 환경 변수를 감싼 스크립트가 있고, 그것을 건너뛰고 러너를 직접 부르면 통과가 거짓이 된다
- **한 번의 Bash 호출이 5분(300초)을 넘게 기다리지 않는다.** 오래 걸리는 것은 백그라운드로 돌리고 4분 이하로 끊어 여러 번 확인한다. `until ... done` 같은 폴링 루프를 5분 넘게 돌리지 않는다
- **서브에이전트에게도 그대로 전달한다.** 이 절은 오케스트레이터만의 규칙이 아니다

**이것이 이 워크플로우에서 가장 큰 절감이다.** 개입 실험에서 이 제약 하나로 소요 시간이 62%, 과금 성격 토큰이 65% 줄었다. 몸통은 기다린 시간 자체가 아니라 **기다리는 동안 프롬프트 캐시가 만료돼 컨텍스트를 다시 만드는 비용**이다. 근거는 `ref/incidents.md`.

## 요청 수를 줄인다

캐시 읽기가 비용의 60% 이상을 차지하고, 읽기는 `요청 수 × 그 시점 컨텍스트`에 비례한다. **요청 하나를 아끼는 것은 그 시점 컨텍스트 전체를 한 번 덜 읽는 것이다.**

- **검증 게이트를 한 번의 Bash 호출로 묶는다.** 테스트·타입 검사·린트·포맷·정적 분석을 따로따로 돌리지 않는다. 하나가 실패해도 나머지를 마저 돌리고 결과를 한 번에 받는다
- **같은 파일을 두 번 읽지 않는다.** 이미 읽은 파일을 고친 뒤 확인이 필요하면 전체를 다시 읽지 말고 변경된 부분만(`diff` 또는 `grep`) 본다
- **여러 파일을 읽어야 하면 한 번의 응답 안에서 병렬로 호출한다.** 한 번에 하나씩 순차로 읽지 않는다
- **git 상태 확인은 경계 시점에만 한다** — 커밋, 리뷰 요청, 판정. 작업 중간에 반복하지 않는다. 위 "검토 대상을 고정한다"의 세 지점이 그 경계다

실측으로 게이트 묶기만으로 한 회차에서 Bash 호출 46건을 순절감했다(총비용의 약 13%). **서브에이전트에게도 그대로 전달한다.**

## 커밋 · PR

**커밋은 오케스트레이터가 한다.** `developer`는 작업 트리만 남긴다 — 판정 시점 지문과 대조하는 것은 리뷰 결과를 쥔 쪽만 할 수 있다.

- **의미 단위로 나눈다.** 기본 단위는 계획서의 단계 하나, 계획이 없었으면 "한 문장으로 설명되는 변경 하나". **`git add -A`를 습관으로 쓰지 않는다** — 커밋할 파일을 경로로 지정한다
- **각 커밋 시점에 프로젝트의 verify(린트·포맷·타입 검사)가 통과해야 한다.** `--no-verify`로 우회하지 않는다. 스테이징하지 않은 작업 중인 파일이 훅을 깨뜨리면 `git stash -k -u`로 치운 뒤 커밋하고 `git stash pop`으로 되돌린다 — **`-u`를 빼지 마라**, 추적되지 않은 새 파일이 원인이면 `-k`만으로는 또 실패한다
- **pre-commit 훅은 대개 인덱스가 아니라 작업트리를 검사한다.** 그래서 부분 스테이징으로 나눠 커밋할 때 훅 통과가 "스테이징된 내용이 verify를 통과한다"를 보장하지 않는다 — 스테이징한 내용은 깨졌는데 작업트리에서 이미 고쳐 놨으면 훅은 그대로 통과한다. 나눠 커밋한 뒤에는 각 커밋이 verify를 통과하는지 직접 확인해라
- **테스트와 그것을 통과시키는 구현은 같은 커밋에 넣는다.** TDD는 작업 순서의 규약이고 커밋 분할의 규약이 아니다. 쪼갤 수 없으면 합친다
- 제목은 한국어로 무엇을 했는지, 본문에는 **왜**를 적는다. 무엇을 바꿨는지는 diff가 말한다

PR은 `gh pr create --base {기준 브랜치}`로 만들고 **base를 반드시 명시한다.** 제목은 `[{JIRA-KEY}] {요약}`. 본문은 프로젝트 PR 템플릿을 따르되, 템플릿이 없으면 네 섹션 — `Jira 이슈 링크 URL` / `배경 (문제 & 원인)` / `작업 상세 (해결)` / `테스트 방법 (기대 결과)`. 여기에 **리뷰 라운드 수와 고쳐진 지적, 남은 `minor` 전체, 규약에 남길 값어치가 있는 것**을 적는다. 본문은 HEREDOC으로 전달한다. assignees·reviewers·labels를 임의로 지정하지 않는다.

**계획서와 개발 루프 기록(`docs/plan/`, `docs/dev-loop/`)은 커밋하지 않는다.** 남길 값어치가 있는 것은 PR 본문에 올려야 살아남는다. **PR을 만들 때 기록의 "다음 사람이 알아야 할 함정" 절을 훑어 둘로 처리한다** — 작업을 넘어 유효한 것은 영구 자리(이 플러그인 `ref/` 또는 프로젝트의 참조 문서)로 옮기고, 도구로 막을 수 있는 것은 후속 작업으로 만든다. "후속 검토"라고 적어 두기만 하는 것은 금지다 — 같은 후속이 두 작업의 기록에 두 번 적히고 두 번 다 실행되지 않은 실측이 있다(`ref/incidents.md`). 옮기지 않은 기록은 그 작업과 함께 죽는다.

## 기록 (티어 2만)

`docs/dev-loop/{YYYY-MM-DD}-{JIRA-KEY 또는 브랜치 이름}.md`에 남긴다. **100줄 상한.** 다섯만 적는다 — **목표**(요청 원문), **판단이 갈린 지점과 결론**, **넘긴 `minor`**, **절차에서 나온 것**, **다음 사람이 알아야 할 함정**.

**다섯 번째는 라운드마다 누적한다.** 인자가 넘어가지 않아 "0 files"로 통과해 버리는 포맷터, baseline을 모르고 기존 진단을 새 것처럼 뱉는 검사, 대상을 통째로 mock 해 회귀를 전혀 잡지 못하는 spec 같은 것들이다. **다음 라운드가 같은 자리에 다시 빠지는 것을 막고, 사람이 이어받을 때도 이 절이 가장 먼저 필요하다.**

**작성 주체는 셋 다다 — 오케스트레이터, `developer`, `reviewer` 모두 이 문서에 내용을 덧붙일 수 있다.** 각자 자기 라운드의 판단(반박과 그 근거, 판정 이유, 계획과 달리 간 것)을 그 자리에서 덧붙이고, 전체 정리와 상한 관리는 오케스트레이터가 책임진다. 라운드가 끝날 때마다 그 자리에서 덧붙인다 — 마지막에 몰아 쓰면 루프가 끊길 때 통째로 날아간다. 병렬 트랙에서는 통합 워크트리 한 곳에 모은다(`ref/parallel.md`).

## 쓰는 방식 — 축약하지 않는다

**이 규칙은 코드 주석만이 아니라 내놓는 글 전부에 적용된다.** 사용자 응답, 커밋 메시지, PR 본문, 계획서, 에이전트끼리 주고받는 보고까지다.

- **축약어를 쓰지 않는 것이 기본이다.** 처음 한 번 풀고 그 뒤로 줄이는 것도 안 된다 — 같은 글 안에서도 반복해서 풀어 쓴다. 표·목록·코드 블록 주석에서 다시 나올 때는 특히. 줄일 수밖에 없다면 `RLS(Row Level Security, 행 단위 접근 제어)`처럼 괄호로 원어와 뜻을 붙인다
- **널리 쓰이는 것도 이 저장소 밖에서 온 것이면 푼다.** `DTO`, `FK`, `PK`, `TDD`처럼 익숙해 보이는 것도 처음 접하는 사람에게는 암호다
- **오류 코드와 식별자는 그대로 쓰되 뜻을 옆에 적는다.** `P2002`(고유 제약 위반)처럼. 프로젝트 내부 용어("티어 2", "지문")를 사용자에게 쓸 때도 무엇을 뜻하는지 한 번 적는다
- **결론보다 상황을 먼저 쓴다.** "이런 일이 생길 수 있다 → 그래서 이렇게 했다" 순서다
- **표는 이미 문장으로 설명한 것을 정리할 때만 쓴다**

## 멈출 때와 끝날 때는 알림을 보낸다

이 루프는 서브에이전트 하나가 수 분에서 십수 분을 쓰므로 **그 사이 사용자가 떠나 있는 것이 기본값**이다. 아래 세 자리에서는 `AskUserQuestion`만 띄우지 말고 시스템 알림(`PushNotification` 등 가용 수단)을 함께 보낸다 — 확인이 필요해 멈출 때, 루프가 끝나 PR을 냈을 때, 3라운드를 넘겨 사용자 판단이 필요할 때. 메시지는 200자 아래 한 줄로, **무엇을 결정해야 하는지를 앞에 둔다.** 라운드마다 진행을 알리지는 않는다.

## 오케스트레이터가 하지 않을 것

- **직접 구현하지 않는다.** 메인 세션이 짠 코드는 리뷰 대상에서 빠진다
- **직접 계획서를 쓰지 않는다.** 조사와 설계를 메인 세션이 하면 그 판단이 검토 없이 구현으로 넘어간다
- **지적을 미리 걸러내지 않는다**
- **`developer`의 보고서를 `reviewer`에게 넘기지 않는다**
- **에이전트의 보고를 그대로 믿지 않는다.** 특히 "다 됐다"는 verify 실행 결과로 확인한다
- **같은 대상에 두 에이전트를 동시에 띄우지 않는다**
- **남이 점유한 워크트리를 임의로 이어받지 않는다**
- **사용자를 기다리며 멈출 때 알림 없이 두지 않는다**
