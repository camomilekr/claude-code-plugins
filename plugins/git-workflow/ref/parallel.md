# 병렬 트랙 개발 (티어 2)

**트랙을 나누기로 정한 뒤에만 적용한다.** 정하는 기준이 아래 진입 조건이고, 애매하면 단일 트랙으로 기운다 — 순차는 느릴 뿐이고, 잘못 나눈 병렬은 통합에서 터져 모든 트랙의 작업을 함께 위험에 빠뜨린다.

계획서가 파일 집합이 서로소인 그룹을 제시하면 그룹마다 워크트리를 따로 만들어 `developer`↔`reviewer` 루프를 동시에 돌린다. 그룹 하나를 **트랙**이라 부른다.

```
{기준 브랜치}
  └─ feature/{KEY}                      통합 브랜치 · .worktrees/{KEY}
       │  (선행 단계를 여기서 먼저 순차로 끝낸다)
       ├─ feature/{KEY}-todos           트랙 · .worktrees/{KEY}-todos
       └─ feature/{KEY}-notifications   트랙 · .worktrees/{KEY}-notifications
```

**PR은 통합 브랜치 하나만 낸다.**

## 진입 조건 — 다섯을 모두 만족할 때만

| 조건 | 확인 |
|---|---|
| **단일 트랙으로 90분을 넘길 규모**라고 계획서가 판단했다 | 이것이 첫 관문이다. 워크트리 준비와 통합 비용이 이득을 넘기 쉽다 |
| 계획서가 파일 집합 **서로소**인 그룹을 2개 이상 제시했다 | 오케스트레이터가 목록을 직접 대조한다 |
| 각 트랙이 **혼자서 프로젝트 verify를 통과**할 수 있다 | 계획서의 단계별 "완료 판정" |
| 공유 인터페이스(타입·상수·시그니처)가 **선행 단계로 이미 끝났다** | 선행 단계가 통합 브랜치에 커밋돼 있다 |
| 트랙이 **3개 이하**다 | 오케스트레이터의 관리 한계. 트랙 3개면 왕복이 최대 18번이다 |

쓰지 말아야 할 때: 계획서 그룹이 하나뿐 / 파일 집합이 겹친다 / 구현 파일과 테스트 파일이 다른 그룹에 있다(TDD가 쪼개진다) / 공유 시그니처가 미확정 / 넷 이상 필요 / 사용자가 결과를 빨리 보고 판단하려 한다.

## 왜 워크트리를 나누는가

같은 워크트리에서 `developer` 둘을 동시에 돌리면 안 된다. 파일이 겹치지 않아도 안 된다. **verify(린트·타입 검사)가 프로젝트 전역이기 때문이다.**

- **TDD가 서로를 깨뜨린다.** A가 실패하는 테스트를 먼저 써 둔 상태에서 B가 verify를 돌리면 A 때문에 깨진다. B는 자기 코드가 잘못됐는지 알 수 없다
- **타입 검사와 린트는 파일 단위로 나눌 수 없다**
- **pre-commit 훅이 서로의 커밋을 막는다.** 우회할 수 없는 교착이다
- **`git add -A`가 남의 파일을 삼킨다**

## 진행 순서

### 1. 선행 단계를 통합 브랜치에서 먼저 끝낸다

공유 인터페이스는 병렬 전에 단독으로 처리하고 **커밋한다.** 트랙들이 이 커밋을 base로 삼는다 — 워크트리는 커밋된 것만 가져간다. 선행 단계가 없으면 건너뛴다.

### 2. 트랙 워크트리를 만든다

**base는 기준 브랜치가 아니라 통합 브랜치의 현재 커밋이다.**

```bash
git worktree add .worktrees/{KEY}-todos         -b feature/{KEY}-todos         feature/{KEY}
git worktree add .worktrees/{KEY}-notifications -b feature/{KEY}-notifications feature/{KEY}
```

의존성 설치·훅 등 프로젝트별 워크트리 준비 절차가 있으면 트랙마다 수행하고, **트랙마다 점유 표식**(기록 파일의 헤더 등)을 남긴다 — 병렬에서는 워크트리가 여러 개라 표식 없는 워크트리 하나가 사고의 입구가 된다.

트랙 이름은 그 트랙이 맡은 **도메인이나 관심사**로 짓는다(`todos`, `notifications`, `config`). `a`, `b`, `1`, `2`는 쓰지 않는다. **계층으로 나누지 마라** — controller/service처럼 가르면 파일 집합이 같은 도메인 폴더 안에서 겹친다. **트랙 경계는 폴더(도메인) 경계와 같아야 한다.**

### 3. 트랙마다 루프를 돌린다

`rules/core.md`의 루프를 그대로 돈다. 달라지는 것은 동시성뿐이다.

| | 같은 트랙 안 | 다른 트랙끼리 |
|---|---|---|
| `developer`와 `reviewer` | **동시 금지** | 상관없다 |
| `developer` 둘 | 있을 수 없다 | **동시 진행이 병렬의 목적이다** |

**트랙끼리 라운드를 맞추지 마라.** A가 3라운드, B가 1라운드여도 정상이다. 동기화하려고 기다리게 하면 병렬의 이득이 사라진다.

`developer`에게 넘길 때 **맡은 단계와 건드릴 파일 범위**를 명시하고 마지막 문장을 빠뜨리지 마라.

```
계획서: docs/plan/2026-08-04-{KEY}-plan.md
맡는 단계: 단계 2, 단계 4
건드릴 파일: src/todos/todos.service.ts, src/todos/todos.service.spec.ts
이 범위 밖의 파일은 다른 트랙이 동시에 작업 중이다. 필요해지면 고치지 말고 보고해라.
```

**`reviewer`의 비교 기준은 기준 브랜치가 아니다.** `git diff feature/{KEY}...HEAD`로 준다 — 기준 브랜치와 비교하면 선행 단계의 변경까지 들어와 이번 트랙이 하지 않은 것을 지적한다.

트랙별 상태(브랜치·라운드·상태·검토 대상 지문)를 표로 관리한다. 지문은 트랙마다 따로 찍는다 — 워크트리가 다르므로 서로 영향받지 않는다.

### 4. 트랙이 끝나면 오케스트레이터가 커밋한다

트랙 워크트리에서 지문을 리뷰 판정 시점과 대조하고, verify를 돌린 뒤, 커밋할 파일을 경로로 지정해 커밋한다. 트랙 안에서도 계획서의 단계를 의미 단위로 삼아 나눠 커밋한다.

### 5. 모든 트랙이 끝난 뒤 한꺼번에 병합한다

하나 끝날 때마다 병합하면 나머지 트랙의 base가 흔들리고, 통합 verify가 어느 트랙 때문에 깨졌는지 가려내기 어려워진다.

```bash
cd .worktrees/{KEY}
git merge --no-ff feature/{KEY}-todos
git merge --no-ff feature/{KEY}-notifications
```

**`--no-ff`를 쓴다.** 병합 커밋이 트랙 경계를 히스토리에 남긴다. 파일 집합이 서로소였다면 **충돌은 나지 않는다.** 났다면 계획서 검증이 실패한 것이다 — 손으로 풀기 전에 무엇이 겹쳤는지 기록에 남겨라.

### 6. 통합 verify는 건너뛸 수 없다

**파일이 겹치지 않아도 논리는 겹친다.** A가 만든 시그니처를 B가 다르게 가정했다면 각 트랙에서는 통과하고 통합에서 처음 깨진다. 이것이 병렬의 유일한 진짜 위험이고 이 관문이 그것을 잡는다.

깨지면 **오케스트레이터가 직접 고치지 않고 통합 워크트리에서 `developer`를 새로 띄운다.** 트랙의 `developer`를 재사용하지 않는다 — 한쪽 맥락만 가진 에이전트는 자기 트랙이 옳다고 보는 방향으로 고친다. 넘기는 것은 계획서 경로, verify 실패 출력 **원문**, 관련 트랙과 각 트랙이 맡았던 단계다.

### 7. 푸시와 PR

통합 브랜치에서만 푸시한다. **트랙 브랜치는 푸시하지 않는다** — 이미 통합에 들어 있고, 원격에 쌓이면 무엇이 살아 있는 작업인지 알 수 없게 된다.

PR 본문에 **트랙 구성**(이름, 맡은 단계, 리뷰 라운드 수)과 **통합 라운드에서 무엇이 깨졌고 어떻게 고쳤는지**를 적는다. 뒤쪽이 다음 계획에 가장 값어치 있는 정보다.

### 8. 정리

트랙 워크트리는 통합이 끝난 직후, 통합 워크트리는 PR이 머지된 뒤에 지운다 (`git worktree remove`).

## 기록은 통합 워크트리 한 곳에 모은다

트랙마다 기록을 따로 남기면 워크트리를 지울 때 흩어진 기록을 각각 꺼내야 하고, 트랙 간 상호작용(통합 라운드에서 무엇이 깨졌는지)을 적을 자리가 없다.

단일 출처는 통합 워크트리의 기록 파일이다. 트랙 워크트리의 `docs/dev-loop/`에는 점유 표식만 남기고 `- **기록 위치**: 통합 워크트리` 한 줄을 덧붙인다. 기록에 트랙별 섹션과 통합 섹션을 더한다. `rules/core.md`의 100줄 상한은 트랙 수만큼 늘려도 된다 — 다만 늘어나는 것은 **트랙별 판단**이어야 하고 verify 출력이 아니다.
