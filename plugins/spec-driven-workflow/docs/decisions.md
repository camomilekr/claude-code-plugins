# 구현 결정 기록 — 설계서 12절 미해결 질문의 해소

> 작성: 2026-08-19 (v0.2.0 구현 세션). `docs/design.md` 12절의 각 항목을 어떻게 결정했고 왜 그랬는지를 남긴다.

## (1) reviewer 지적 반영 후 종료 조건 → **blocker에 한해 재검토 1회 허용**

- `major`는 설계 원안대로 수정 1회 → G1·G2 재실행 → 종료(재검토 없음). `major`의 정의(지금은 동작하지만 곧 문제)는 놓친 경계 조건·빠진 테스트류라 수정 결과를 기계 게이트로 확인할 수 있는 비중이 크다.
- `blocker`는 정의상 "동작이 틀렸거나 보안 문제이거나 규약 위반"이고, 이 중 설계 이탈·보안 경계류는 **수정이 해소됐는지를 기계 게이트만으로 확신할 수 없다.** blocker에 한해 재검토 1회를 허용하되 범위를 "blocker 해소 여부 + 그 수정이 만든 회귀"로 좁힌다.
- 왕복 퇴화 방지: 재검토는 어떤 경우에도 1회다. 재검토에서 또 blocker가 나오면 파이프라인을 멈추고 사용자에게 보고한다. blocker가 없는 회차에는 추가 비용이 0이므로 예측 1(총비용 1.3배 이하)을 위협하지 않는다.

## (2) 스펙 매니페스트 형식 → **JSON 확정**

`docs/plan/{YYYY-MM-DD}-{KEY}.spec-manifest.json`. G2(`scripts/spec-guard.sh`)가 결정론적 스크립트라 기계 파싱이 우선이다. 사람 가독용 수치는 dev-loop 기록에 요약으로 남긴다. 스키마는 `rules/core.md`의 "스펙 매니페스트" 절이 정본이다.

## (3) PreToolUse 훅의 단계 판별 → **보류 (M4 그대로)**

설계 원안대로 커밋 전 스크립트 검사(G2 1단계)가 안정된 뒤에만 검토한다. 훅 입력에서 서브에이전트 유형을 식별할 수 있는지 확인이 선행 조건이라는 판단도 유지한다.

## (4) 스펙 컴파일 의존성 → **(a) 채택: spec-writer가 최소 인터페이스 선언까지 작성**

- spec-writer는 스펙이 컴파일되는 데 필요한 **최소 선언**(타입, 인터페이스, 함수 시그니처)을 쓸 수 있다. "구현 코드를 쓰지 않는다"의 경계: 본문은 `throw new Error("not implemented")` 또는 그에 준하는 미구현 표시까지만 허용, 분기·계산·상태를 담으면 위반이다.
- 이 파일들은 매니페스트의 `scaffoldFiles`에 별도 등재한다. **G2 무변경 검사 대상은 `specFiles`뿐이다** — scaffold는 developer가 구현으로 채우는 파일이므로 수정이 정상이다.

## (5) 스펙 커밋의 주체 → **오케스트레이터가 `scripts/spec-commit.sh`로 커밋**

- git-workflow의 "커밋은 오케스트레이터가 한다" 규율을 유지한다. 스크립트가 매니페스트의 `specFiles`+`scaffoldFiles`**만** 스테이징해 커밋하고(경로 지정 규율), 커밋 해시를 매니페스트의 `specCommit`에 기록한다 — G2 기준점 고정을 LLM 손이 아니라 스크립트에 맡긴다.
- 매니페스트 자체(`docs/plan/`)는 커밋하지 않는다(기존 규율 계승). 스펙 커밋 시점에는 verify(린트·타입)가 통과해야 하고, 테스트는 red가 정상이다.

## (6) 티어 1에서 G2 생략 → **설계 원안 수용, 실험 관찰 항목으로 유지**

티어 1은 매니페스트가 없으므로 G2가 없다. developer의 TDD red 실측 의무(에이전트 규칙)와 G1 + G3(diff 한정 1회)로 커버한다. 실험에서 티어 1 작업의 껍데기 테스트 발생 여부를 관찰한다.

## (7) "같은 종류 major → 구조 변경" 규칙의 이식 → **트리거를 "한 보고 안의 반복"으로 재정의**

라운드가 없으므로 트리거를 둘로 옮긴다: (a) G3 보고에서 **같은 종류의 지적이 서로 다른 자리 3곳 이상**에 나오면, reviewer가 구조 변경 후보로 명시하고 오케스트레이터는 developer 재호출 프롬프트에 "사례별 수정 대신 구조 변경을 먼저 검토하라"를 넣는다. (b) 연속된 작업 회차에서 같은 종류가 반복되는 것은 함정 이관 규칙(0.2.9 계승, PR 시점 영구 자리 이동)이 담당한다.

## 스펙-테스트 간극 보완 (docs/spec-test-gap.md 5절) — 2026-08-19 2차 반영

스펙과 스펙 테스트는 동치가 아니다(스펙 테스트는 스펙의 실행 가능한 부분의 유한 표본이다)라는 분석에 따라, 간극의 성분별로 다음을 결정했다.

- **5-1 채택 — 문구 교정**: "완료의 정의" → "종료 조건(필요조건)"으로 전 구현 파일 교정. green이 증명하는 것은 표본의 만족까지이고 구현 대상은 계획서의 의도임을 `rules/core.md`·`agents/developer.md`에 명문화. 표본 과적합(하드코딩 분기로 표본만 통과) 금지를 developer 규칙에 추가. 게이트 초록불의 의미 한정("요구사항 충족의 증명이 아니다")을 게이트 절에 추가
- **5-2 채택 — 누락 패턴 자문**: spec-writer에 검증 항목당 실패 경로·경계·동시성 3문 자문을 의무 절차로 추가. 근거는 실험 4차의 저장 실패 경로 누락(두 방법론 공통, 리뷰 3라운드도 미검출)과 0.2.9 함정 프롬프트 이관의 실증(기록이 아니라 프롬프트에 있어야 실행된다)
- **5-3 채택 — 요구사항 추적표**: 매니페스트에 `plan`·`covers` 필드 추가, architect의 검증 항목 ID(V1, V2, …)에 안정성 규칙(재배열 금지·결번 유지) 추가. **검사 위치는 G2가 아니라 `spec-commit.sh`(스펙 커밋 직전)** — 과소포괄은 developer가 구현을 시작하기 전에 잡는 것이 가장 싸고, 스펙이 동결되는 지점이 검사의 자연스러운 자리다. 검사 내용: 계획서의 모든 `[테스트]` 항목이 최소 1개 스펙에 매핑 + 계획서에 없는 ID 참조 거부 + 계획서에서 항목 표를 못 찾으면 형식 위반으로 명시적 실패(침묵 통과 금지)
- **5-4 보류 — G3에 스펙 공백 탐지 항목 추가**: 검토 항목을 늘리는 것이 검출을 늘린다는 보장이 없다는 실측(4차의 "함정으로 짚고도 놓침")에 따라, 5-2·5-3으로 공백을 앞단에서 줄이는 것을 우선하고 실험에서 G3 검출률을 본 뒤 판단
- **5-5 채택 (선택 게이트) — mutation testing**: `.claude/spec-workflow.json`에 `commands.mutation`을 선언한 프로젝트에서만 G1이 함께 실행. 타임아웃은 `mutationTimeoutSeconds`(기본값 `timeoutSeconds`). 과적합(F1)과 빈약한 단정의 기계 검출기이며, 계약-값 분리에 그대로 들어맞아 플러그인 쪽 비용이 거의 0이다
- **5-6 보류 — 스펙 이중 서명**: 에이전트 층을 늘려 플러그인의 존재 이유(층 줄이기)와 충돌. 스펙 오류(F3) 기인 결함이 실험에서 실제로 관측될 때만 검토

## 추가 결정 — 설계서에 명시되지 않았던 것

- **G1·G2 실패 처리 상한**: 게이트 실패 → 실패 출력 원문을 들려 새 developer 재호출 → 게이트 재실행. **같은 게이트가 3회 연속 실패하면** 멈추고 사용자에게 보고한다.
- **질문 게이트의 위치**: architect 계획서가 나온 직후 1회다. 요약 확인 + 계획서의 "확정하지 못한 것"을 몰아서 묻고, 이후 파이프라인은 무인으로 진행한다. (접수 시점에는 통상 물을 것이 없고, 미확정 요구사항은 조사 후에야 드러난다)
- **Jira 연동은 이 플러그인의 범위 밖**: 티켓 조회는 설치된 조회 수단(스킬·MCP)을 쓰고, 상태 전환 규칙은 규정하지 않는다. 설계서 9절 스캐폴드가 `rules/core.md` 하나만 규정한 것을 따른다.
- **reviewer는 verify·테스트를 재실행하지 않는다**: G1이 직전에 결정론적으로 실행했으므로 재실행은 요청 수 낭비다(git-workflow에서 reviewer가 직접 돌리던 것은 developer의 자기 보고를 못 믿어서였고, 여기서는 스크립트 출력이 근거다). 체크리스트 항목 검증에 실행이 필요한 경우만 예외다.

## spec-driller 스킬 구현 (docs/spec-driller.md 8절 미해결 질문) — 2026-08-19 (v0.4.0)

1. **brainstorming 스킬과의 관계 → 순차(발산 후 수렴), 대체 아님**: brainstorming은 "무엇을 만들 것인가"를 만드는 발산 도구이고, spec-driller는 만들기로 정한 것의 구멍을 찾는 수렴 도구다. 요구사항이 문장으로 존재하면 driller 단독으로 충분하고, 아이디어 단계면 발산이 먼저다 — SKILL.md의 "쓰지 않는다"에 명시했다. 실험 팔 비교에서는 driller 사용 여부만 변수로 두고 brainstorming은 양 팔에서 동일 취급한다.
2. **질문 상한 → 8개**: `AskUserQuestion`이 호출당 최대 4문항이므로 연속 2회까지 허용한다. 넘치면 선별을 조여 상위 8개만 남기고 나머지는 "가정"으로 기록한다. 상한이 없으면 사람 시간 비용이 무한정 늘고, 상한이 4면 실측 누락 유형(실패 경로·경계·동시성)만으로도 차기 쉽다.
3. **기각된 질문의 기록 → 남기지 않는다**: 감사 가능성보다 문서 무게를 우선한다. 단, 선별 탈락 중 기록 가치가 있는 것은 설계 4절 ③ 그대로 "가정: X로 진행" 목록으로 남긴다 — 사용자가 훑어보다 이의를 제기하면 그것이 곧 감사다.
4. **탐침 목록의 갱신 절차 → probes.md에 명문화**: (1) 모든 층을 통과해 놓친 결함의 원인 질문이면 1회 발생으로도 자격 (2) 그 외에는 서로 다른 작업에서 2회 이상 반복 (3) 저장소 고유 함정이 아니라 일반 질문으로 일반화해 등재.
5. **착수 보류 미결의 처리 → 사용자에게 묻는 것이 기본값**: 스킬 완료 보고(⑥) 시점에 `AskUserQuestion`으로 (a) 미결에 의존하지 않는 부분만 범위 절단 착수 (b) 전체 보류를 묻는다. (a)를 택하면 architect가 해당 부분을 계획에 넣지 않고 "확정하지 못한 것"에 올린다(agents/architect.md에 규칙 추가). 잘린 범위가 나중 결정과 충돌하는 위험은 사용자가 (a)를 고르는 시점에 감수한 것으로 본다.

검증 방법론(superpowers writing-skills의 선별 채택): CSO description 규칙(트리거만, 절차 요약 금지)과 규율 조항에 대한 **baseline 압박 테스트 1회 + 채록한 합리화의 명시적 봉쇄**는 가져오고, 모든 편집에 테스트를 요구하는 Iron Law 절대주의는 버렸다(비결정적 테스트의 비용 대비 효용 불일치). `ref/probes.md`의 함정 축적 구조가 writing-skills의 합리화 표 축적 패턴과 동형이라 별도 도입은 불필요하다. 실측 2건 (2026-08-19, 결함 6종을 심은 동일 요구사항 표본):

- **baseline(스킬 없음, 시간 압박 + 결정권자 부재 + "알아서 채워라" 위임)**: 심은 모순 2건을 질문 없이 해석으로 해소, 제품 결정 11건을 스스로 내림, 확인 필요 항목을 4필드 없는 "판단 노트"로 뭉갬, "착수 가능" 선언. 채록한 합리화 6종을 SKILL.md "합리화 봉쇄" 표로 명시 봉쇄
- **GREEN(스킬 적용, ①~③ 수행)**: 심은 결함 전량 검출(모순 2건 질문화, 타임존·실패 경로·상태 전이·경계), 상한 8개 준수, 선택지 전부 제안형, 한계 명시 준수. 자가 보고된 경계 사례 2건(범위를 정하는 침묵을 가정으로 강등)과 피드백 5건(상한 초과 시 우선순위, 신규 기능의 질문 부풀림, `{KEY}` 공백, 탐침 적용 단위, 유보 선택지)을 REFACTOR로 반영

구현 배치: 스킬 본체 `skills/spec-driller/SKILL.md`, 탐침 정본 `ref/probes.md`(spec-writer 자문 절차와 공유 — 설계 7절 "목록이 두 곳에 살면 한쪽만 자라는 날이 온다"에 따라 spec-writer의 자문 목록을 probes.md 참조로 전환). 미결 상속 경로는 설계 3-4절대로 `rules/core.md`(spec-writer·G3 입력, PR 본문), `agents/architect.md`(확정 조항 1차 소스 + 미결 ID 표기), `agents/spec-writer.md`(미결 스펙화 금지 + 매니페스트 `assumptions` 선택 필드), `agents/reviewer.md`(임시 가정 이탈 검사)에 배선했다.

## PLAT-568 5차·5-1차 실측 반영 — 2026-08-21 (v0.4.1)

5차(0.4.0 그대로, $48.28 · 397요청 · CodeRabbit MAJOR 2)에서 드러난 결함 4건을 규칙·스크립트로 고쳐 같은 티켓에서 한 번 더 돌렸다(5-1차: $38.57 · 358요청 · 재생성 0 · MAJOR 1). 라운드 추가 없이 판정 규칙만 이식하는 것이 설계 의도였고, 비용은 늘지 않았다.

1. **감수 기록은 심각도 하향의 근거가 아니다** (`rules/core.md` G3 절, `agents/reviewer.md`): 정상 흐름에서 데이터가 조용히 유실되는 경로는 구현자가 "감수"로 적었어도 major 이상. 감수를 승인할 권한은 질문 게이트의 사용자에게만 있다. 5차 실측: 구현자가 감수로 기록한 "저장 진행 중 연속 편집 유실"을 검토가 minor 로 넘겼고 CodeRabbit 이 같은 자리를 MAJOR 2건으로 올렸다. **5-1차 실측의 한계**: 구현자가 감수로 적지 않고 반만 고친 뒤 해결로 보고한 경우(같은 행 저장 요청의 순서 역전)는 이 규칙이 발동하지 않았다. 판정 규칙은 "하향"을 막지 실패의 "미인지"를 막지 못한다 — 다음 후보는 spec-writer 체크리스트에 "동일 대상 비동기 저장이 겹칠 수 있으면 순서 보장 주체를 검증 항목으로 적는다"를 넣는 것이다.
2. **재호출은 언제나 새 스폰이다** (`rules/core.md` 4곳 + "하지 않을 것"): developer 뿐 아니라 architect·spec-writer 도 `SendMessage` 재개 금지. 5차 실측: 재개 2건이 컨텍스트 재생성 412,920 토큰을 냈고 그 회차 방법론 내부 재생성의 전부였다. 5-1차: `SendMessage` 0건, 재생성 0.
3. **경로 매치 프로브** (`scripts/gate-verify.sh`): specFiles 경로가 실재하지 않으면 exit 2, 결합 test 통과 시 specFiles 를 경로별로 단독 재실행해 러너가 조용히 건너뛴 경로(`*.spec.ts` 미포함 설정 등)를 잡는다. `--skip-path-probe` 로 끈다. `vitest list` 방식은 3분 타임아웃으로 기각. 5-1차에서 무음 통과가 "돌았다/건너뛰었다"를 로그로 구분하지 못해, 전부 통과 시 `[PASS] path-probe (N/N 경로 단독 매치)` 한 줄을 남기도록 했다.
