# spec-driller 스킬 설계 초안

> 작성: 2026-08-19. 상태: **구현됨 (v0.4.0)** — 스킬 본체는 `skills/spec-driller/SKILL.md`, 탐침 정본은 `ref/probes.md`, 8절 미해결 질문의 결정은 `docs/decisions.md`에 있다. 이 문서는 설계 근거로 보존한다. 배경이 되는 간극 분석은 `docs/spec-test-gap.md`가 정본이고, 이 스킬은 그 문서의 실패 모드 F2(과소포괄)·F3(스펙 오류)를 요구사항 단계에서 공격하는 장치다.

## 0. 한 줄 정의

**요구사항 문서를 구조화된 탐침으로 파헤쳐 모순·엣지케이스·누락을 질문으로 만들고, 사용자의 결정을 받아 문서에 조항으로 기입하는 대화형 스킬.** 질문 생성기 + 결정 기록기다 — 그 이상이 아니다.

## 1. 왜 필요한가 — 파이프라인이 덮지 못하는 위층

파이프라인의 검증은 아래로 갈수록 기계적이고 위로 갈수록 비어 있다.

| 층 | 결함 유형 | 검증 장치 |
|---|---|---|
| 구현 ↔ 스펙 | 스펙 위반, 스펙 약화 | G1·G2 (기계, 강함) |
| 계획 ↔ 스펙 | 계획 결함, 항목 누락 | spec-writer 백지 관점 + 추적 검사 |
| 요구사항 ↔ 계획 | 계획이 요구사항을 오해 | spec-writer 계획 결함 보고 (약함) |
| **요구사항 그 자체** | **모순, 엣지케이스 미정, 암묵 가정** | **(비어 있음)** — 이 스킬의 자리 |

요구사항의 결함은 가장 싼 지점이자 가장 비싼 지점이다 — 착수 전에 고치면 문장 몇 줄이고, green까지 통과한 뒤 드러나면 "모든 게이트가 초록불인데 요구사항이 충족되지 않은 상태"(spec-test-gap.md 7절)가 된다. spec-writer의 백지 관점은 **계획**의 결함을 잡지 **요구사항**의 결함을 잡지 못한다 — 잘못된 요구사항을 충실하게 스펙으로 옮길 뿐이다.

실측 근거: 실험 4차에서 두 팔 모두 놓친 저장 실패 경로는 코드의 결함이기 전에 **요구사항에 실패 경로 조항이 없었던 것**이다. reviewer 3라운드도, 함정 프롬프트 이관도 못 잡았다 — 아무도 물어보지 않은 질문은 어느 층에서도 답해지지 않는다.

## 2. 형식 — 왜 파이프라인 단계가 아니라 스킬인가

**파이프라인에 넣지 않는다.** 에이전트 층을 늘리는 것은 이 플러그인의 존재 이유(층 줄이기)와 충돌한다 — spec-test-gap.md 5-6(스펙 이중 서명)을 보류한 것과 같은 이유다. 스킬은 다르다:

- **사용자가 호출하는 선택적 도구**라 무인 파이프라인의 비용 구조를 건드리지 않는다
- **대화형이 본질**이다 — 이 스킬의 산출물은 사람의 결정이고, 그것은 무인 구간에 있을 수 없다
- git-workflow 티어 2가 architect 앞에 brainstorming(요구사항 확정)을 두는 것과 **같은 슬롯**이라, 두 플러그인의 실험 비교가 공정하게 유지된다

## 3. 핵심 원칙 세 가지 — 이것이 깨지면 스킬이 아니라 짐이다

### 3-1. 답하지 말고 물어라

"저장이 실패하면 어떻게 되어야 하는가"는 코드에서 도출할 수 없는 **제품 결정**이다. 스킬이 스스로 답을 채우면 spec-writer의 맹점이 spec-driller의 맹점으로 자리만 옮긴 것이다. 이 스킬의 가치는 날카로운 질문으로 **사람의 판단을 강제로 소환하는 것**이고, 답의 정본은 사용자다.

- 각 질문에는 선택지를 붙이되(결정 비용을 낮추기 위해), 선택지는 제안이지 답이 아니다
- 사용자가 결정하지 못한 항목은 **"미결"로 명시해 문서에 남긴다.** 미결을 지우거나 기본값으로 채우는 것은 금지다 — 미결이 명시되어 있으면 spec-writer가 체크리스트로 넘기고 G3가 확인하지만, 조용히 채워지면 아무도 다시 보지 않는다. 미결의 형식과 파이프라인 처리는 3-4절

### 3-2. 산출물은 대화가 아니라 문서 수정이다

파헤친 결과가 세션 대화에만 남으면 architect는 받지 못한다. 완료 조건은 **결정이 요구사항 문서에 조항으로 기입되고, 각 조항에 결정 근거 한 줄이 남는 것**이다.

- 산출 위치와 이름은 규칙이다: **`docs/plan/{YYYY-MM-DD}-{KEY}-requirements-drilled.md`** (`{KEY}`는 계획서·매니페스트와 같은 규칙 — Jira 키 또는 브랜치 이름에서 `feature/`를 뗀 부분). 형제 산출물(`{YYYY-MM-DD}-{KEY}.spec-manifest.json`, `-checklist.md`)과 명명 체계를 맞췄고, `-drilled` 접미사가 드릴링을 거친 산출물임을 표시해 원시 요구사항과 구분한다. 파일명에 "spec"을 쓰지 않는 것은 의도다 — 이 플러그인에서 스펙은 실행 가능한 테스트를 가리키고, 이 문서는 그 위층인 요구사항이다. 층 구분이 파일명에서부터 지켜져야 한다
- `docs/plan/`인 것도 의도다 — 이 문서는 계획서와 같은 생애주기(작업 산출물, 커밋 금지, 값어치 있는 것은 PR 본문으로 이관)를 탄다. 문서 머리에 "spec-driller로 보강됨, 대상 원문: {출처}"를 남긴다
- 수정 가능한 대상 문서가 이미 저장소에 있으면(요구사항 마크다운) 새 파일 대신 그 문서를 직접 보강해도 된다. 티켓 본문·구두 요청처럼 저장소 밖이 출처면 위 규칙의 새 파일로 떨군다
- 수정 형식: 원문은 보존하고 **"확정 조항"(결정된 것)과 "미결 항목"(사용자가 보류한 것) 섹션을 추가**한다. 원문을 고쳐 쓰면 무엇이 원래 요구이고 무엇이 드릴링의 산물인지 구분이 사라진다

### 3-3. 탐침은 자유연상이 아니라 정본 목록이다

질문을 즉흥으로 만들면 회차마다 품질이 흔들리고, 발견된 함정이 축적되지 않는다. 탐침 목록을 **플러그인 `ref/probes.md`에 정본으로 두고**, 이 스킬과 spec-writer(5-2 자문 절차)가 **같은 목록을 공유한다.** 같은 탐침을 요구사항 레벨에서는 사람에게 묻고(spec-driller), 스펙 레벨에서는 에이전트가 자문한다(spec-writer) — 이중 방어이고, 실전에서 함정이 추가되면 두 층이 같이 강해진다. PR 시점 함정 이관(0.2.9 계승)의 영구 자리 중 하나가 이 목록이다.

초기 탐침 목록 (ref/probes.md의 시드):

| 탐침 | 묻는 것 | 예 |
|---|---|---|
| 모순 | 조항끼리 충돌하는가, 같은 말이 다른 뜻으로 쓰였는가 | "삭제하면 기록도 지운다" vs "기록은 불변이다" |
| 실패 경로 | 각 동작이 실패하면 무엇이 보여야 하는가. 부분 성공은 가능한가 | 저장 실패, 외부 API 타임아웃, 트랜잭션 중단 (실험 4차의 실측 누락 유형) |
| 경계 | 범위의 양 끝, 빈 것과 없는 것, null과 0 | 목표치 0인 할 일, 빈 목록, 최대 길이 |
| 동시성·순서 | 같은 일이 두 번 일어나면, 순서가 뒤바뀌면 | 중복 제출, lost-update (PLAT-581 reviewer의 실측 검출 유형) |
| 암묵 가정 | 문서가 말하지 않고 전제하는 것은 | 타임존(이 계열 저장소의 대표 함정), 권한, 단일 사용자 가정 |
| 상태 전이 | 어떤 상태에서 이 동작이 금지되는가, 되돌리기는 | 완료된 항목의 수정, 삭제 후 복원 |
| 규모·성능 | 10배가 되어도 같은 답인가 | 목록이 1만 건일 때의 페이지네이션 |

### 3-4. 미결은 소멸하지 않는 체크리스트로 남긴다

사용자가 그 자리에서 답할 수 없는 질문이 반드시 나온다 — 타 팀의 의사결정이 필요하거나, 이해관계자 확인이 필요하거나, 지금은 정보가 없는 경우다. 이 스킬은 그런 항목을 **체크리스트 형식으로 문서에 첨부하는 것까지가 일이다.** "나중에 확인"이라고 대화에만 남기는 것은 금지다 — 같은 후속 조치가 두 번 기록되고 두 번 다 실행되지 않은 실측(0.2.9의 근거)이 있고, 체크리스트가 문서에 붙어 있어야 파이프라인의 다음 층들이 그것을 상속한다.

형식 (요구사항 문서의 "미결 항목" 섹션):

```markdown
## 미결 항목 (spec-driller)

- [ ] UD-1 저장이 부분 실패하면 사용자에게 무엇이 보이는가
      결정 주체: 플랫폼팀 (@아무개) · 막는 것: 검증 항목 V-3, V-7
      임시 가정: 전체 롤백 + 재시도 안내로 진행 (가정으로 진행 가능)
- [ ] UD-2 비활성 사용자의 데이터 보존 기한
      결정 주체: 법무 검토 · 막는 것: 검증 항목 V-12
      임시 가정: 없음 — **이 항목에 의존하는 부분은 착수 보류**
```

각 항목의 필수 필드는 넷이다: **질문**, **결정 주체**(누가 답할 수 있는가 — "나중에"가 아니라 사람·팀·절차를 지목한다), **막는 것**(어느 검증 항목이 이 답에 의존하는가 — 5-3 추적표와 같은 ID 체계를 쓴다), **임시 가정**(그 가정으로 작업을 진행할 수 있는지, 아니면 의존 부분의 착수를 보류해야 하는지). 추적 링크(티켓·스레드)가 있으면 붙인다.

파이프라인의 상속 경로 — 미결이 각 층에서 어떻게 다뤄지는지가 이 형식의 존재 이유다:

- **architect**: 미결에 의존하는 검증 항목은 실행 가능 여부와 무관하게 미결 ID를 표기한다
- **spec-writer**: **미결에 걸린 항목을 스펙 테스트로 굳히지 않는다.** 답이 안 나온 것을 단정으로 고정하는 것이 정확히 F3(스펙 오류)의 제조법이다. "임시 가정으로 진행 가능" 항목만 가정을 매니페스트에 명시하고 스펙화하며, 가정이 뒤집히면 스펙 수정 절차(spec-writer 재호출)를 탄다
- **G3(reviewer)**: 미결 체크리스트가 검토 범위에 들어간다 — 미결에 의존하는 코드가 임시 가정 밖으로 나갔는지 본다
- **PR**: 미결 목록을 **PR 본문에 그대로 싣고**, 타 팀 결정 대기 항목은 후속 작업으로 만든다 — 0.2.9 이관 규칙과 같은 원리다. 계획서·기록은 커밋되지 않으므로 PR 본문에 오르지 않은 미결은 그 작업과 함께 죽는다

## 4. 동작 절차

**입력 출처는 가리지 않는다.** 사용자가 처음 제공하는 요구사항은 Jira 티켓일 수도, Notion 문서일 수도, GitHub 이슈일 수도, 저장소 안 마크다운일 수도, 그냥 프롬프트로 직접 친 텍스트일 수도 있다. 스킬은 출처별 도구(Jira·Notion MCP, `gh issue view`, `Read`, 대화 내용)로 읽되, **산출물은 출처와 무관하게 3-2절 규칙의 파일 하나로 수렴한다.** 외부 출처(Jira·Notion·이슈)의 원본을 고치러 가지 않는다 — 권한과 동기화 문제는 스킬 범위 밖이고, 산출 문서 머리에 출처 링크를 남기는 것으로 잇는다. 원본 반영이 필요하면 사용자가 한다.

```
입력: 요구사항 (위 출처 중 무엇이든 — 경로, URL, 티켓 키, 또는 대화 텍스트)
① 읽기      요구사항 + (있으면) 관련 도메인의 CONTEXT.md·기존 스펙을 읽는다
② 드릴링    ref/probes.md의 탐침을 조항마다 적용해 질문 후보를 만든다
③ 선별      "답이 구현을 갈라놓는 질문"만 남긴다 (아래 기준)
④ 질문      AskUserQuestion으로 몰아서 묻는다 — 선택지 포함, 여러 번 나누지 않는다
⑤ 기입      결정을 확정 조항으로, 보류를 미결 항목으로 문서에 추가한다
⑥ 보고      추가된 조항 수, 미결 수, 다음 단계(architect 호출) 안내
```

③ 선별 기준이 이 스킬의 품질을 결정한다. 묻는 것은 **답에 따라 계획·스펙·구현이 달라지는 질문**뿐이다. "답이 무엇이든 구현이 같다"거나 "코드베이스를 읽으면 알 수 있다"거나 "관례적 기본값이 있고 그걸 벗어날 이유가 없다"면 묻지 않는다 — 질문 수가 늘수록 사용자의 주의력이 흐려지고, 질문 게이트를 한 번에 몰아 끝내는 규약(무인 구간 확보)이 깨진다. 선별에서 떨어진 질문 중 기록할 값어치가 있는 것은 묻지 않고 "가정: X로 진행"으로 문서에 남겨 사용자가 훑어볼 수 있게 한다.

## 5. 호출 시점과 티어

- **티어 2 작업의 architect 호출 전**이 기본 자리다. `rules/core.md`의 티어 2 절차에 "요구사항이 문서로 확정되지 않았거나 사용자가 원하면 spec-driller를 먼저 쓴다"로 연결한다 — **의무가 아니라 권장**이다. 의무로 만들면 요구사항이 이미 명확한 작업에 사람 시간을 강제로 물리게 된다
- 티어 0·1에는 걸지 않는다
- 파이프라인 밖 단독 사용도 가능하게 설계한다 — 요구사항 문서 보강은 이 플러그인 없이도 유용하다. 스킬이 파이프라인 상태(매니페스트, 계획서)에 의존하지 않아야 한다

## 6. 비용과 한계 — 정직하게

**비용은 토큰이 아니라 사람 시간이다.** 파이프라인의 무인 구간을 사는 대신 앞단의 유인 구간을 늘리는 교환이다. 그래서 선별(③)이 엄격해야 하고, 실험에서는 driller에 쓴 사람 시간을 측정 항목에 넣어야 팔 간 비교가 공정하다.

**이 스킬도 탐침의 유한 표본이다.** 탐침 목록 자체의 맹점은 남는다 — F2·F3를 **줄이는** 장치이지 없애는 장치가 아니다. "driller를 통과했으니 요구사항은 완전하다"는 새로운 초록불 착시를 만들지 않도록, 스킬의 완료 보고에 "이 확인은 탐침 목록의 범위 안이다"를 명시한다. spec-test-gap.md가 "껍데기 테스트 0건" 예측에서 경계한 것과 같은 함정이다.

**드릴링 결과의 신선도.** 확정 조항은 그 시점의 결정이다. 작업 중 요구가 바뀌면 문서를 다시 드릴링하는 것이 아니라 바뀐 조항만 갱신한다 — 스킬 재실행을 요구사항 변경의 관문으로 만들지 않는다.

## 7. 구현 노트

- 위치: 이 플러그인의 `skills/spec-driller/SKILL.md` (플러그인이 스킬을 배포하는 표준 경로). 탐침 정본은 `ref/probes.md`
- SKILL.md frontmatter의 `description`은 호출 판단 기준이 되므로 "요구사항 문서의 모순·엣지케이스·누락을 질문으로 만들어 사용자 결정을 받아 문서를 보강한다. 티어 2 착수 전 또는 요구사항이 애매할 때"처럼 **언제 쓰는지**를 담는다
- 스킬은 메인 세션에서 실행된다(서브에이전트가 아니다) — AskUserQuestion을 쓸 수 있어야 하기 때문. 드릴링으로 메인 컨텍스트가 커지는 것이 걱정되면, ①~②(읽기·질문 후보 생성)만 서브에이전트에 위임하고 ③~⑤(선별·질문·기입)를 메인이 하는 분리를 검토할 것
- spec-writer와의 연결: 5-2(표준 누락 패턴 자문)를 구현할 때 자문 목록을 `ref/probes.md` 참조로 바꾼다 — 목록이 두 곳에 살면 한쪽만 자라는 날이 온다
- 요구사항 문서에 "확정 조항"·"미결 항목" 섹션이 있으면 architect가 그것을 검증 항목의 1차 소스로 쓰도록 architect 규칙에 한 줄 추가한다

## 8. 미해결 질문 — 구현 세션이 결정할 것

1. **brainstorming 스킬과의 관계**: superpowers의 brainstorming이 세션에 있으면 역할이 겹친다. 대체인가(드릴링이 브레인스토밍을 포함), 순차인가(브레인스토밍으로 발산 → 드릴링으로 수렴), 택일인가. 실험 팔 구성에도 영향이 있으니 명시적으로 정할 것
2. **질문 상한**: ④에서 한 번에 묻는 질문 수의 상한(예: 8개)을 둘 것인가. AskUserQuestion은 호출당 최대 4문항이라 그 배수로 정해진다
3. **드릴링 기록의 위치**: 확정·미결 외에 "물었으나 기각된 질문"을 남길 것인가. 남기면 감사 가능성이 생기지만 문서가 무거워진다
4. **탐침 목록의 갱신 절차**: PR 시점 함정 이관에서 probes.md로 옮기는 판단 기준 — 어떤 함정이 탐침이 될 자격이 있는가(한 번 발생 vs 반복 발생)
5. **착수 보류 미결의 처리**: "임시 가정 없음 — 착수 보류" 항목이 있을 때 티어 2 파이프라인을 시작할 수 있는가. 선택지 — (a) 미결에 의존하지 않는 부분만 범위로 잘라 착수 (b) 전체 보류. (a)면 architect가 범위를 자르는 규칙이 필요하고, 잘린 범위가 나중에 결정과 충돌할 위험을 감수한다. 사용자에게 물어 정하는 것이 기본값일 것
