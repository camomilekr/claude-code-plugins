# spec-driven-workflow 설계서

> 작성: 2026-08-19. 작성 시점 기준 git-workflow 소스는 0.2.9다.
> 이 문서는 구현을 시작하는 세션이 다른 맥락 없이 읽고 착수할 수 있도록 쓴 정본이다. 결정된 것과 결정을 미룬 것(12절)을 구분해 두었다.

## 0. 한 장 요약

git-workflow의 developer ↔ reviewer **왕복 대화 루프**를 없애고, 검증을 세 층으로 재배치한 단방향 파이프라인이다.

1. **완료 기준을 구현 전에 고정한다** — spec-writer가 새 컨텍스트에서 실패하는 테스트(스펙)를 먼저 쓴다
2. **1차 방어선은 결정론적 게이트다** — verify·테스트·스펙 무결성 검사를 스크립트로 강제한다
3. **LLM 검토는 새 컨텍스트로 1회다** — 왕복하지 않고, 스펙이 못 덮는 것만 본다

에이전트에게 부탁하던 것(스펙을 고치지 마라, 테스트가 실제로 실패하는지 확인해라)을 **훅과 스크립트가 강제하는 것**으로 바꾸는 것이 핵심이다.

**명시적 한계 — 스펙 테스트는 완료 기준과 동치가 아니다.** 스펙 테스트는 스펙 중 실행 가능한 부분의 **유한 표본**일 뿐이다. green이 증명하는 것은 "스펙의 표본을 만족했다"이지 "요구사항을 만족했다"가 아니며, **요구사항 대비 스펙 자체의 공백은 이 파이프라인의 어떤 결정론적 게이트도 기계적으로 잡을 수 없다** — spec-writer의 백지 관점과 G3 검토에만 기댄다. 이 간극의 해부와 보완 과제는 `docs/spec-test-gap.md`가 정본이다.

## 1. 왜 별도 플러그인인가

git-workflow와의 **통제 비교 실험**이 목적이다. git-workflow를 직접 고치면 대조군이 사라진다. git-workflow는 동결하고, 이 플러그인을 실험 4-2차(가칭)의 세 번째 팔로 세워 같은 작업을 수행시킨 뒤 시간·토큰·비용·결함 검출을 비교한다(11절).

다만 git-workflow에서 **실증이 끝난 레버는 그대로 계승한다** — 바꾸는 것은 "루프 구조"이지 "검증 그 자체"가 아니다.

- 테스트 실행 제약: 경로 지정 강제 + 300초 상한 (0.2.5 — 시간 −62%·토큰 −65%)
- 검증 게이트 묶기로 요청 수 절감 (0.2.5)
- dev-loop 인계 문서 규정 (0.2.5)
- **전용 워크트리 강제** (0.2.8): 코드 작업은 티어와 무관하게 전용 워크트리에서 한다. 근거(남의 변경과의 diff 오염)는 루프 구조와 무관한 작업 공간 위생이고, 이 플러그인에서는 G2 무변경 검사와 G3가 보는 diff의 기준점을 보호한다
- **함정의 프롬프트 이관** (0.2.9): 발견된 함정은 기록 파일로 갈음하지 않고 이후 모든 에이전트 프롬프트에 그대로 옮긴다 — 재발 0건·프롬프트당 500~1,000토큰 실측. 단계 간 통신이 파일인 이 설계에서도 함정만은 예외로 프롬프트에 싣는다(다음 에이전트는 기록을 읽지 않지만 프롬프트는 반드시 읽는다)
- **PR 시점 함정 이관** (0.2.9): 기록의 "다음 사람이 알아야 할 함정" 절을 영구 자리(플러그인 `ref/` 또는 프로젝트 참조 문서)로 옮기거나 후속 작업으로 만든다. "후속 검토"라고 적어 두기만 하는 것은 금지
- 티어 시스템 (판정 조건 동일 — 7절)

## 2. 근거 — 실험 실측

근거 보고서는 전부 `~/projects/whatap-front/docs/`에 있다 (`plat-557-three-way-comparison.md`, `plat-581-methodology-comparison.md`, `plat-659-methodology-comparison.md`, `methodology-experiment-4-comparison.md` 등).

| 실측 | 수치 | 출처 |
|---|---|---|
| 계획+구현 코어 비용은 단순 절차와 사실상 동일 | 5% 차이 (910,457 vs 866,535 토큰) | PLAT-581 |
| 비용 격차의 몸통은 오케스트레이터 + reviewer 두 층 | 총액의 57.6% | PLAT-581 |
| 리뷰 대기 중 developer 캐시 만료가 재생성의 몸통 | 재생성 771,672의 77% | 실험 4차 |
| 라운드마다 developer를 새로 띄우면 같은 구간 비용 감소 | 요청당 −40%, 라운드당 −24.7%, 맥락 상실 0건 | PLAT-581 3-2차 |
| 리뷰 3라운드를 돌고도 외부 품질 지표는 단순 절차와 동수 | CodeRabbit MAJOR 2:2 | 실험 4차 |
| 계획-구현 컨텍스트 분리만으로 계획 결함 검출 | 3건 (reviewer 없이) | PLAT-557 |
| 독립 reviewer만 잡은 결함 유형 | "통과하지만 아무것도 검증하지 않는 테스트", lost-update 경합 | PLAT-581 |

여기서 나오는 설계 판단:

- **왕복 루프는 걷는다.** 격차의 몸통이고, 한계 효용이 최신 실험일수록 낮게 측정된다 (외부 연구도 검증 루프 1~2라운드가 도달 가능한 개선의 75%를 잡는다고 보고한다)
- **컨텍스트 경계는 늘린다.** 검증력의 실증된 원천은 "역할 프롬프트"가 아니라 "깨끗한 컨텍스트가 산출물만 보는 것"이다. Cognition의 실측(리뷰어가 코더와 컨텍스트를 공유하지 않을 때만 효과적, Devin Review PR당 평균 2건 검출·58% 중대)과 일치한다
- **reviewer의 실증 가치 중 최대 조각(껍데기 테스트 검출)은 구조로 대체한다.** 스펙 작성자와 구현자를 분리하면 "자기 테스트를 자기가 채점하는" 이해충돌이 사라져, 검출할 껍데기 테스트가 애초에 만들어지지 않는다 (5-2절)
- **git-workflow의 실증 가치 세 가지(자력 검출·무인 실행·판단 이력)는 보존한다.** 각각 스펙+게이트+검토 1회, 게이트 앞 질문 몰기, dev-loop 계승으로 잇는다

업계 근거 (요약): Cognition [Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents) · [Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working), Addy Osmani [Agent Harness Engineering](https://addyosmani.com/blog/agent-harness-engineering/)("성공은 조용히, 실패는 시끄럽게" — 결정론적 게이트 우선), GitHub Spec Kit·Amazon Kiro의 스펙 주도 개발(완료 기준을 코드보다 먼저 고정), [Claude Code 공식 모범 사례](https://code.claude.com/docs/en/best-practices)(탐색→계획→구현 단방향, 서브에이전트는 읽기 격리용, 검증은 훅).

## 3. 설계 원칙

1. **쓰는 손은 하나다.** 코드를 고치는 에이전트는 어느 시점에도 developer 하나뿐이다. 병렬 쓰기 없음
2. **검증의 1차 방어선은 결정론적 게이트다.** 기계로 잡을 수 있는 것을 LLM에게 묻지 않는다
3. **LLM 검증은 새 컨텍스트로, 왕복 없이 산다.** 검증자는 산출물(계획서·diff)만 보고, 지적은 파일로 전달되며, 재검토 사이클은 상한 1회다
4. **완료의 정의는 구현 전에 실행 가능한 형태로 고정한다.** "다 됐는지"를 두고 사후에 다툴 여지를 사전에 제거한다. 단 고정되는 것은 완료 기준의 **실행 가능한 표본**이지 완료 그 자체가 아니다 (0절의 한계, `docs/spec-test-gap.md`)
5. **단계 간 통신은 대화가 아니라 파일이다.** 각 단계는 새 컨텍스트로 뜨고, 이전 단계의 산출물 파일만 읽고, 자기 산출물 파일만 남기고, 종료한다. **단계 사이에 살아있는 서브에이전트를 두지 않는다** — 리뷰 대기 중 캐시 만료(실험 4차 재생성의 77%)라는 비용 항목 자체를 구조적으로 소멸시킨다

## 4. 파이프라인 (티어 2 기준)

```
[메인 세션: 요청 접수 → 티어 판정 → 질문 몰아서 게이트 1회]
        │
        ▼
① architect          새 컨텍스트. 요구사항 스냅샷 + 계획서 작성 (docs/plan/)
        │                계획서에 "검증 항목" 섹션 필수 (5-1절)
        ▼
② spec-writer        새 컨텍스트. 요구사항+계획서만 읽음.
        │                실패하는 스펙 테스트 작성 → red 실측 → 매니페스트 기록
        │                부산물: 계획 결함 보고 (있으면 architect 1회 재호출 판단)
        │                산출물을 스펙 커밋으로 고정
        ▼
③ developer          새 컨텍스트. 계획서+스펙만 읽음. 스펙을 green으로 만든다.
        │                스펙 파일 수정 금지 (G2가 강제). 완료 후 종료
        ▼
④ 게이트 G1          스크립트. verify + 테스트(경로 지정·300초 상한) + e2e
        ▼
⑤ 게이트 G2          스크립트. 스펙 무결성 — 스펙 파일 무변경 + 전부 green (6-2절)
        ▼
⑥ 게이트 G3          reviewer 1회. 새 컨텍스트, diff+계획서+체크리스트만.
        │                blocker/major 있으면: developer 1회 재호출 → G1·G2 재실행 → 종료.
        │                재검토 없음. minor는 기록만
        ▼
[메인 세션: 커밋·PR → 외부 게이트(CodeRabbit·CI)]
```

| 단계 | 컨텍스트 | 읽는 것 | 남기는 것 |
|---|---|---|---|
| architect | 새로 | 요청, 코드베이스 | 요구사항 스냅샷, 계획서 |
| spec-writer | 새로 | 요구사항, 계획서 | 스펙 테스트(red), 매니페스트, 체크리스트, 계획 결함 보고 |
| developer | 새로 | 계획서, 스펙, dev-loop | 구현 코드, dev-loop 기록 |
| reviewer | 새로 | diff, 계획서, 체크리스트, dev-loop | 검토 보고 (dev-loop에 추가) |
| 메인 세션 | 상주(얇게) | 산출물 경로만 | 티어 판정, 게이트 실행 기록 |

메인 세션은 **배선만 한다** — 전용 워크트리 생성(0.2.8 계승), 단계 호출, 산출물 경로 전달, 게이트 스크립트 실행. 조사·구현·품질 판단을 직접 하지 않는다. 서브에이전트 보고서 전문을 컨텍스트에 쌓지 않고 산출물 파일 경로로 받는다. 단 하나의 예외가 **함정 전파**(0.2.9 계승)다 — 앞 단계가 보고한 함정(조용한 실패, 거짓 통과, 파괴적 명령)은 이후 모든 단계의 프롬프트에 그대로 옮긴다.

## 5. 에이전트 명세

이름은 비교 가능성을 위해 git-workflow와 맞춘다 (architect·developer·reviewer는 유지, spec-writer만 신규).

### 5-1. architect (git-workflow에서 개작)

git-workflow의 `agents/architect.md`를 기반으로 하되:

- **유지**: 구현 금지, `Write`는 `docs/plan/` 두 문서 한정, 테스트 작성 금지, 언어 규칙
- **추가**: 계획서에 **"검증 항목" 섹션을 필수로** 넣는다. "무엇이 참이면 이 작업이 끝난 것인가"를 관찰 가능한 동작 단위로 나열한 목록이다. spec-writer의 입력이 되므로, 각 항목에 (a) 실행 가능한 테스트로 표현 가능한지 (b) 불가능하면 왜인지를 표시한다
- **변경**: 계획서 검증을 reviewer 왕복이 아니라 spec-writer가 겸한다 (spec-writer가 계획을 백지에서 다시 읽으며 결함을 발견하는 것이 PLAT-557이 실증한 "컨텍스트 경계 = 검증 장치"다)

### 5-2. spec-writer (신규)

frontmatter 초안:

```yaml
---
name: spec-writer
description: 요구사항 스냅샷과 계획서만 읽고, 완료 기준을 실패하는 스펙 테스트로 고정한다.
  구현 코드를 쓰지 않고, red를 실측해 기록하며, 스펙 매니페스트와 체크리스트를 남긴다.
  계획서의 결함을 발견하면 보고서에 명시한다. 파이프라인의 사전 검증 담당이다.
tools: Read, Write, Grep, Glob, Bash
model: inherit
---
```

규칙 (에이전트 본문에 담을 것):

- **입력은 요구사항 스냅샷 + 계획서 + 코드베이스 읽기뿐이다.** architect·developer의 대화 이력을 받지 않는다 — 백지 상태가 이 에이전트의 검증력의 원천이다
- **산출물 네 가지**:
  1. **스펙 테스트** — 계획서의 검증 항목을 실패하는 테스트로 옮긴다. 파일 위치·이름은 대상 저장소의 테스트 규약을 따른다
  2. **스펙 매니페스트** — `docs/plan/{이름}.spec-manifest.json`. 스펙 파일 경로 목록 + 각 파일의 red 실측 기록(실행 명령, 실패 출력 요지) + 스펙 커밋 해시 자리
  3. **체크리스트** — 실행 가능한 테스트로 표현할 수 없는 검증 항목(UI 확인, 마이그레이션 절차 등)의 목록. 게이트 G3(reviewer)의 검토 범위가 된다
  4. **계획 결함 보고** — 계획서대로면 검증 불가능하거나 모순인 항목. 있으면 메인 세션이 architect 1회 재호출을 판단한다
- **red를 실측한다.** 스펙 테스트를 실제로 실행해 실패를 확인하고, 실패 출력 원문을 매니페스트에 인용한다. 실행하지 않은 스펙은 산출물이 아니다. **처음부터 통과하는 스펙은 그 자체로 결함이다** — 이미 구현돼 있거나(계획 결함으로 보고) 아무것도 검증하지 않는 것이다
- **관찰 가능한 동작만 고정한다.** 반환값, 던지는 예외, 거절하는 입력, 경계 조건. 내부 구조(호출 순서, 함수 분해, mock 호출 인자)를 스펙에 박지 않는다 — 구현자의 설계 자유를 남겨야 하고, 실측(PLAT-659)에서 더 나은 구조적 수정은 자유도가 있는 쪽에서 나왔다
- **구현 코드를 쓰지 않는다.** `Write`는 테스트 파일과 위 산출물에만 허용. 스펙이 컴파일되기 위한 최소한의 타입·인터페이스 선언이 필요한 경우의 처리는 12절 미해결 질문 (4)
- 산출물은 **스펙 커밋으로 고정한다** (커밋 주체는 메인 세션이어도 된다 — 12절 (5)). 이 커밋이 G2 diff 검사의 기준점이다

### 5-3. developer (git-workflow에서 개작)

- **유지**: 언어 규칙, 커밋 규율, dev-loop 기록, 테스트 실행 제약(경로 지정·300초)
- **변경 (핵심)**: **단계의 종료 조건이 바뀐다** — "계획서를 구현했다"가 아니라 "스펙 매니페스트의 모든 테스트가 green이고 verify가 통과한다"이다. 단 이것은 **필요조건이지 완료의 정의가 아니다** — green은 스펙 표본의 만족이지 요구사항 충족이 아니고(0절 한계), 구현 대상은 여전히 계획서의 의도다. 스펙 테스트만 통과하는 최소 구현으로 좁히는 것(표본 과적합)은 금지이고 G3의 검토 대상이다 (`docs/spec-test-gap.md`)
- **추가**: **스펙 매니페스트에 등재된 파일을 수정하지 않는다.** 스펙이 틀렸다고 판단되면 수정하지 말고 dev-loop에 근거와 함께 기록하고 멈춘다 — 메인 세션이 spec-writer 재호출 또는 사용자 에스컬레이션을 판단한다. 이 금지는 부탁이 아니라 G2가 결정론적으로 강제한다
- **추가**: 스펙 밖의 테스트(구현 중 발견한 경계 조건 등)는 자유롭게 추가한다. 매니페스트 밖이므로 G2 대상이 아니다
- **삭제**: 라운드 개념. developer는 한 번 떠서 완료하고 종료한다. reviewer 지적 반영이 필요하면 **새 developer가** dev-loop(인계 문서)를 읽고 뜬다 — 3-2차에서 맥락 상실 0건으로 실증된 방식이다

### 5-4. reviewer (git-workflow에서 개작 — 게이트 G3)

- **유지**: 코드 수정 금지(`Edit`는 dev-loop 전용), 심각도 등급(blocker/major/minor), 언어 규칙
- **변경 (핵심)**: **호출 상한 1회.** 왕복 루프가 없다. 지적 반영 후 재검토도 없다 — 반영 검증은 G1·G2 재실행이 대신한다
- **변경**: 검토 범위를 좁힌다. 스펙과 게이트가 이미 덮은 것(요구사항 충족 여부, 테스트 존재 여부)을 다시 보지 않고, **스펙이 못 덮는 것만** 본다:
  1. spec-writer가 남긴 **체크리스트** 항목
  2. **보안·권한 경계·경합 조건·횡단 관심사** — 실측에서 reviewer만 잡은 lost-update 경합류
  3. **설계 품질** — 계획서 대비 구조 이탈, 규약 위반
- 판정 규칙: blocker·major → developer(새 컨텍스트) 1회 재호출로 수정 → G1·G2 재실행 → 종료. minor → dev-loop에 기록만, 수정하지 않는다

## 6. 게이트 명세

### 6-0. 실행 주체 계약 — 플러그인과 프로젝트의 분담

게이트를 설계하기 전에 답해야 하는 질문이 둘 있다. "플러그인은 프로젝트의 테스트 명령을 모르는데 어떻게 실행하는가"와 "게이트가 결과를 판단할 수 있는가"다.

**게이트는 기계적 사실만 판정한다. 의미 판단이 필요해지는 순간 설계 위반이다.**

게이트가 다루는 판정은 전부 기계적 사실로 환원된다 — 명령의 exit code, `git diff --name-only`의 파일 목록, 매니페스트 파일의 존재. 실패의 **원인 해석과 대응**("왜 깨졌고 어떻게 고칠까")은 게이트의 일이 아니라 그 출력을 받는 에이전트의 일이다. 게이트는 이진 판정 + **실패 출력 원문의 전달자**이고, 그 이상의 지능이 필요해지면 그것은 게이트가 아니라 네 번째 에이전트다 — 기계로 환원되는 검증은 전부 G1·G2로, 환원되지 않는 잔여(설계 품질, 체크리스트)만 G3로 보내는 것이 층위의 논리다.

**프로젝트 종속성은 CI와 같은 방식으로 푼다 — 계약과 값의 분리.**

CI 러너가 프로젝트의 테스트 명령을 모르면서도 동작하는 것은 "프로젝트가 workflow 파일에 명령을 선언한다"는 계약 덕분이다. 같은 패턴을 쓴다.

- **플러그인이 정의하는 것 (계약)**: "이 플러그인을 쓰는 프로젝트는 검증 명령을 선언해야 한다"는 인터페이스와, 선언된 명령을 읽어 실행하고 exit code를 해석하는 게이트 스크립트
- **프로젝트가 제공하는 것 (값)**: 실제 명령. 선언 위치는 프로젝트의 `.claude/spec-workflow.json`(스키마 상세는 구현 시 확정):

  ```json
  {
    "commands": {
      "verify": "npm run verify",
      "test": "npm test -- {paths}",
      "e2e": "npm run test:e2e"
    },
    "timeoutSeconds": 300
  }
  ```

- **선언이 없으면 게이트는 "설정 없음"으로 명시적으로 실패한다.** 침묵 통과는 금지다 — 게이트가 없는데 있는 것처럼 보이는 것이 최악의 상태다. 규칙(`rules/core.md`)에 온보딩 절차를 넣는다: 티어 1 이상 작업의 착수 시점에 설정 부재를 감지하면 사용자에게 물어 설정을 생성하고 진행한다
- 이 분담은 새로운 것이 아니다 — git-workflow(일반 규약)와 사용 저장소의 `.claude/scripts/`(worktree-new.sh, fingerprint.sh)가 이미 같은 구조이고, 그 분담을 게이트까지 확장하는 것이다

**강제력에는 세 층이 있고, 검증마다 어느 층에 둘지를 명시한다.**

| 층 | 강제력 | 근거 |
|---|---|---|
| 규칙 (rules/) | 없음 — LLM이 따르길 기대할 뿐 | 규칙이 주입됐는데도 파이프라인을 통째로 건너뛴 실측이 있다 (PLAT-659 1차 시도, 55만 토큰 폐기) |
| 스크립트 (scripts/) | 약함 — 명령 조합의 변동성은 없애지만 실행은 LLM 몫 | 워크트리 스크립트가 같은 이유로 존재한다 |
| 훅 (hooks/) | 강함 — LLM 바깥에서 결정론적으로 실행, 도구 호출 차단 가능 | git-workflow의 SessionStart 규칙 주입이 이미 이 층이다 |

이 설계의 배치: 게이트 실행 자체는 오케스트레이터 **규칙** + **스크립트**로 시작하고(M3), 스펙 파일 수정 차단은 커밋 전 **스크립트** 검사(M3)에서 `PreToolUse` **훅**(M4)으로 올린다. 프로젝트 쪽 pre-commit(husky 등)에 게이트를 연동하는 것은 프로젝트 재량으로 남긴다 — 플러그인이 프로젝트의 git 훅을 건드리는 것은 계약 밖이다.

### 6-1. G1 — 결정론적 검증 (scripts/gate-verify.sh)

대상 저장소의 검증 명령(verify·테스트·e2e)을 **한 번의 호출로 묶어** 실행하고(요청 수 절감 — 실증 레버 계승), 실패 시 실패 출력만 반환한다. 테스트는 경로 지정·300초 상한을 강제한다. 명령은 6-0의 계약에 따라 프로젝트의 `.claude/spec-workflow.json`에서 읽는다.

### 6-2. G2 — 스펙 무결성 (scripts/spec-guard.sh)

입력: 스펙 매니페스트 경로. 검사 두 가지, 전부 결정론적이다.

1. **무변경 검사**: `git diff --name-only {스펙 커밋}..HEAD`에 매니페스트 등재 파일이 있으면 **실패**. developer가 스펙을 약화시키는 경로를 차단한다
2. **green 검사**: 매니페스트의 모든 스펙 파일을 실행해 전부 통과하면 성공. (red 실측 기록이 매니페스트에 있으므로, "red였던 것이 green이 됐다"가 이 시점에 성립한다)

구현은 두 단계로 나눈다:

- **1단계 (M3, 필수)**: 커밋 전 스크립트 검사. 단순하고 결정론적이다
- **2단계 (M4, 선택)**: `PreToolUse` 훅으로 developer 단계 중 실시간 차단 — `Edit`/`Write` 대상 경로가 매니페스트에 있으면 도구 호출 자체를 거부. 사후 검출보다 낭비가 적지만, "지금이 developer 단계"임을 훅이 알아야 하는 문제가 있다 (12절 (3)). 1단계가 안정된 뒤에만 붙인다

### 6-3. G3 — 검토 1회

5-4절의 reviewer 호출이다. 게이트 순서상 G1·G2 통과 뒤에 호출한다 — 기계가 잡을 것을 LLM에게 보내지 않기 위해서다.

## 7. 티어

git-workflow의 티어 판정 조건을 그대로 계승하고, 절차만 바꾼다.

| 티어 | 조건 (git-workflow와 동일) | 절차 |
|---|---|---|
| 0 | 문서, 설정 한 줄, 조사·질문 | 메인 세션 직접. 변화 없음 |
| 1 | 네 조건 모두 만족 (폴더 2개 이하 등) | spec-writer 생략. developer가 TDD로 직접 (red 실측 의무는 developer 규칙에 있음) → G1 → G3(diff 한정 1회) |
| 2 | 하나라도 어긋남 | 4절 전체 파이프라인 |

주의할 역설 하나: 실험 데이터에서 왕복 루프가 전면 우세였던 유일한 회차는 **작은 버그 수정**(PLAT-659)이었고, 큰 기능일수록 한계 효용이 낮았다. 즉 이 플러그인의 이득은 티어 2에서 가장 클 것으로 예측된다 — 이 예측 자체가 실험 대상이다(11절).

## 8. dev-loop — 판단 이력의 계승

git-workflow의 실증 가치 중 "판단 이력"을 잇는다. `docs/dev-loop/` 기록 규정을 계승하되, 왕복 루프가 없으므로 기록 주체가 바뀐다:

- spec-writer: 계획 결함 보고, red 실측 기록 (매니페스트와 중복되는 수치는 매니페스트가 정본)
- developer: 구현 중 판단, 다음 사람이 알아야 할 함정 (인계 문서 규정 — 0.2.5 실증분 계승)
- reviewer: 검토 보고 전문
- 메인 세션: 게이트 실행 결과, 재호출 판단 근거

PR 시점에는 0.2.9의 이관 규칙을 그대로 따른다 — 기록의 "다음 사람이 알아야 할 함정" 절을 훑어, 작업을 넘어 유효한 것은 영구 자리로 옮기고 도구로 막을 수 있는 것은 후속 작업으로 만든다. 옮기지 않은 기록은 그 작업과 함께 죽는다.

| 단계 | 내용 | 비고 |

"같은 종류의 major 2라운드 연속 → 구조 변경"(0.2.9)은 라운드가 전제라 그대로는 승계할 수 없다 — 취지(사례 수정 대신 구조 변경)를 G3 지적 처리 규칙에 옮길지는 구현 시 판단 (12절 (7)) |

| M4 | (선택) PreToolUse 스펙 가드 훅 | 1단계 안정 후. 12절 (3) 해결이 선행 조건 |

## 11. 실험 설계 — 예측과 반증 조건

측정 항목은 기존 실험(4차)과 동일하게 맞춘다: 소요 시간, 요청 수, 과금 토큰, 실비용, 컨텍스트 재생성 비중, 자력 검출 결함(심각도별), CodeRabbit MAJOR, CI 통과, 사용자 개입 횟수.

**예측** (깨지는 지점이 곧 발견이다):

1. 총비용은 팔 B(스킬 조합) 대비 **1.3배 이하** — 코어는 5% 차이가 실증돼 있으므로, 추가분은 spec-writer 1회 + reviewer 1회뿐이어야 한다
2. 컨텍스트 재생성 비중 **25% 미만** — 단계 사이에 살아있는 에이전트가 없으므로 리뷰 대기 만료 항목이 사라져야 한다
3. **이해충돌형 껍데기 테스트 0건** — red 실측 + 작성자·구현자 분리 + G2가 구조적으로 막는 것은 "자기 코드에 맞춰 통과하기 쉽게 쓴 테스트"라는 유형이다. reviewer나 CodeRabbit이 이 유형을 지적하면 구조의 실패다. 단 **과소포괄형 공백(spec-writer가 생각하지 못한 경로)은 이 예측의 범위 밖이다** — 그 유형은 예측 4로 계측되고, 결함이 나오면 "스펙 공백 기인"으로 분류해 둔다 (`docs/spec-test-gap.md`)
4. CodeRabbit MAJOR는 **팔 A(git-workflow) 이하** — 4차에서 팔 A와 팔 B가 동수(2:2)였으므로, 여기서 더 나오면 왕복 루프가 잡아 주던 것이 있었다는 증거다
5. 무인 실행 구간은 팔 A와 동등 — 질문은 게이트 1회에 몰고, 이후 파이프라인은 개입 없이 진행돼야 한다

**반증 시 해석**: 예측 4가 깨지면(MAJOR 증가) 왕복 루프의 고유 검출 가치가 실증되는 것이고, 그 결함 유형을 분류해 G3의 체크리스트를 보강할지 왕복 1회를 되살릴지 판단한다. 예측 1이 깨지면 spec-writer 비용을 해부한다(계획서 크기, 코드베이스 탐색량).

## 12. 미해결 질문 — 구현 세션이 결정할 것

1. **reviewer 지적 반영 후 종료 조건**: 현재 설계는 "blocker·major → 수정 1회 → G1·G2 재실행 → 종료(재검토 없음)"다. blocker가 수정으로 해소됐는지를 기계 게이트만으로 확신할 수 없는 유형(설계 이탈)이면? 대안: blocker에 한해 재검토 1회 허용. 비용과 4차의 한계 효용 실측을 근거로 판단할 것
2. **스펙 매니페스트 형식**: JSON(`{이름}.spec-manifest.json`, 스크립트 파싱 용이) vs 계획서 마크다운 내 표(사람 가독성). 현재 설계는 JSON — G2가 결정론적 스크립트이기 때문. 확정할 것
3. **PreToolUse 훅의 단계 판별**: 훅이 "지금 developer 단계"임을 아는 방법 — 마커 파일(`docs/plan/.stage`) vs 환경변수 vs 서브에이전트 이름 매칭. 훅 입력에서 서브에이전트 유형을 식별할 수 있는지 Claude Code 훅 명세 확인이 선행돼야 한다
4. **스펙 컴파일 의존성**: 스펙 테스트가 아직 없는 함수·타입을 참조하면 컴파일이 깨진다. 선택지 — (a) spec-writer가 최소 인터페이스 선언(구현 없는 시그니처)까지 작성하고 매니페스트에 별도 표기 (b) 스펙을 `it.todo` + 실행 가능 최소 골격으로 쓰고 developer가 살을 채우되 단정문은 못 바꾸게… (b)는 G2 무변경 검사와 충돌한다. (a) 권장이나 "구현 코드를 쓰지 않는다" 경계의 정의가 필요하다
5. **스펙 커밋의 주체와 브랜치 규율**: spec-writer가 직접 커밋하는가, 메인 세션이 하는가. git-workflow의 커밋 규율(의미 단위, 경로 지정)과의 정합 확인
6. **티어 1에서 G2 생략의 타당성**: 티어 1은 매니페스트가 없어 무변경 검사가 없다. developer 자신이 red를 실측하는 규칙만으로 충분한가 — 실험에서 티어 1 작업이 섞이면 관찰할 것
7. **"같은 종류 major → 구조 변경" 규칙(0.2.9)의 이식**: 원 규칙은 리뷰 라운드의 반복이 트리거인데 이 설계에는 라운드가 없다. 대안 트리거 — G3가 같은 종류의 지적을 여러 자리에서 냈을 때, 또는 연속된 작업 회차에서 같은 종류가 반복될 때. 취지(사례를 하나씩 고치는 작업 자체가 같은 종류의 오류를 새로 만든다)는 유효하므로 버리지 말고 트리거만 재정의할 것
