# 스펙 주도 워크플로우 — 핵심

메인 세션은 **오케스트레이터**이고 **배선만 한다** — 전용 워크트리 생성, 단계 호출, 산출물 파일 경로 전달, 게이트 스크립트 실행. 조사·구현·품질 판단을 직접 하지 않는다. 파이프라인은 `architect`(계획) → `spec-writer`(완료 기준 고정) → `developer`(구현) → 게이트 G1·G2(스크립트) → G3(`reviewer` 1회)의 **단방향**이고, 에이전트 정의는 이 플러그인의 `agents/`에, 게이트 스크립트는 `scripts/`에 있다.

developer ↔ reviewer 왕복 루프가 **없다.** 검증은 세 층이 대신한다:

1. **완료 기준을 구현 전에 고정한다** — `spec-writer`가 새 컨텍스트에서 실패하는 스펙 테스트를 먼저 쓰고 red를 실측한다
2. **1차 방어선은 결정론적 게이트다** — verify·테스트(G1)와 스펙 무결성(G2)을 스크립트가 판정한다. 기계로 잡을 수 있는 것을 LLM에게 묻지 않는다
3. **LLM 검토는 새 컨텍스트로 1회다** — `reviewer`는 스펙과 게이트가 못 덮는 것만 본다

**단계 간 통신은 대화가 아니라 파일이다.** 각 단계는 새 컨텍스트로 뜨고, 이전 단계의 산출물 파일만 읽고, 자기 산출물만 남기고, 종료한다. **단계 사이에 살아있는 서브에이전트를 두지 않는다** — 리뷰 대기 중 프롬프트 캐시 만료로 컨텍스트를 다시 만드는 비용을 구조적으로 없앤다. 서브에이전트 보고서 전문을 컨텍스트에 쌓지 말고 산출물 파일 경로로 받아라. 단 하나의 예외는 아래 "함정 전파"다.

## 흐름 한눈에

```
요청 접수 → 티어 판정 → 전용 워크트리
  ├─ 티어 0: 직접 처리
  ├─ 티어 1: developer(TDD, red 실측) → G1 → G3(diff 한정) → 커밋·PR
  └─ 티어 2:
     ⓪ (선택) spec-driller 스킬 — 요구사항 드릴링. 요구사항이 미확정이거나 사용자가 원할 때
     ① architect      계획서 + 요구사항 스냅샷 (docs/plan/). 계획서에 "검증 항목" 필수
     ② 질문 게이트     사용자 확인은 여기 1회에 몬다. 이후 무인 진행
     ③ spec-writer    실패하는 스펙 테스트 + 매니페스트 + 체크리스트. red 실측
     ④ 스펙 커밋       scripts/spec-commit.sh — G2의 기준점을 고정
     ⑤ developer      스펙을 green으로. 스펙 파일 수정 금지
     ⑥ G1             scripts/gate-verify.sh — verify + 테스트(경로·300초) + e2e 묶음
     ⑦ G2             scripts/spec-guard.sh — 스펙 무변경 + 전부 green
     ⑧ G3             reviewer 1회 — 체크리스트·횡단 관심사·설계 품질만
     → 커밋·PR
```

요청이 Jira 티켓 기반이면 조회는 설치된 조회 수단(스킬·MCP)으로 하고, 본문·첨부를 **원문 그대로** `architect`에게 넘긴다. 상태 전환 규칙은 이 플러그인이 규정하지 않는다.

## 티어 — 무게를 작업 크기에 맞춘다

**조건을 세어서 갈린다.** 애매함을 이유로 무거운 쪽으로 기울지 마라.

| 티어 | 조건 | 절차 |
|---|---|---|
| **0 · 직접** | 규칙·에이전트 정의, 문서, 설정값 한 줄, 오타, 조사·질문 답변 | 메인 세션이 직접. 계획도 게이트도 없다 |
| **1 · 가볍게** | 아래 넷을 **모두** 만족 | spec-writer 생략. `developer` 1회(TDD, red 실측 의무) → G1 → G3(diff 한정 1회) → 커밋·PR. 계획서·기록을 만들지 않는다 |
| **2 · 전체** | 하나라도 어긋남 | 위 전체 파이프라인. 기록을 남긴다 |

티어 1의 네 조건: (1) 건드리는 소스 하위 폴더가 **2개 이하** (2) **새 도메인 타입·영속화 형식 변경 없음** (3) **횡단 관심사가 아님** — 보안·권한 경계, 스케줄·시간대 기준의 날짜 경계처럼 한 곳을 고치면 다른 곳이 어긋나는 종류는 독립 검토가 필요하다 (4) 버그 수정이면 **원인이 확정됐다**.

4번을 특히 조심해라. **수정 범위는 원인이 정한다.** 코드를 읽어 짐작한 것은 확정이 아니다. 사용자가 "바로 고쳐 줘"라고 했으면 그 지시가 티어를 덮는다.

## 작업 공간 — 전용 워크트리를 먼저 만든다, 예외 없다

**코드를 건드리는 작업은 티어와 무관하게 전용 워크트리에서 한다.** 메인 체크아웃에서 브랜치만 새로 파는 것은 규칙 위반이다. 워크트리 생성이 브랜치 생성보다 먼저다.

```bash
git worktree add {워크트리 경로} -b feature/{KEY}-{케밥케이스-설명} {기준 브랜치}
```

`git worktree list`로 기존 명명 규칙을 먼저 확인해 맞춘다. "작업이 가볍다", "메인이 깨끗해 보인다", "사용자가 말하지 않았다"는 전부 건너뛸 이유가 되지 않는다 — 사용자가 **명시적으로 "워크트리 없이 진행"이라고 지시한 경우에만** 예외다. 메인 체크아웃에서 작업하면 남의 변경이 섞여 **G2 무변경 검사와 G3가 보는 diff의 기준점이 오염되고**, 커밋 경로 지정 실수 한 번으로 남의 미커밋 변경이 PR에 실린다.

- **기준 브랜치는 프로젝트가 정한다.** 명시가 없으면 사용자에게 확인한다. 기준 브랜치에 직접 커밋·푸시하지 않는다
- **워크트리 하나에 잡 하나.** 남이 점유한 워크트리(미커밋 변경, 진행 중 프로세스, 계획·기록 파일)를 임의로 이어받지 않는다. "깨끗하다"를 "주인이 없다"로 읽지 마라
- **지문·verify·테스트·게이트 스크립트는 반드시 워크트리 안에서 실행한다.** 셸 위치는 도구 호출 사이에 저장소 루트로 되돌아갈 수 있다 — 루트에서 돌린 테스트는 `No tests found`를 통과처럼 보이게 한다

## 프로젝트 설정 계약 — `.claude/spec-workflow.json`

게이트는 프로젝트의 검증 명령을 모른다. CI와 같은 방식으로 푼다 — **프로젝트가 명령을 선언하고, 게이트 스크립트가 읽어 실행한다.** 선언 위치는 대상 저장소의 `.claude/spec-workflow.json`:

```json
{
  "commands": {
    "verify": "npm run verify",
    "test": "npm test -- {paths}",
    "e2e": "npm run test:e2e",
    "mutation": "npx stryker run"
  },
  "timeoutSeconds": 300,
  "mutationTimeoutSeconds": 1800
}
```

`verify`·`test`는 필수, `e2e`·`mutation`은 선택이다. `test`의 `{paths}` 자리에 스크립트가 대상 경로를 치환한다. `mutation`은 스펙 표본에만 과적합한 구현과 아무 변형도 죽이지 못하는 빈약한 단정의 **기계 검출기**다 — 선언된 프로젝트에서만 G1이 함께 실행하고, 실행 시간이 크므로 그 경우 게이트를 백그라운드로 돌려 나눠 확인한다. **선언이 없으면 게이트는 "설정 없음"으로 명시적으로 실패한다** — 침묵 통과 금지. 티어 1 이상 작업의 착수 시점에 설정 부재를 감지하면, 저장소 문서에서 verify·테스트 명령을 찾아 사용자에게 확인받고 설정 파일을 생성한 뒤 진행한다(질문 게이트에 합쳐도 된다).

## 계획 (티어 2)

요구사항이 문서로 확정되지 않았거나 사용자가 원하면 `architect` 호출 전에 **spec-driller 스킬**(이 플러그인 `skills/spec-driller/`)로 요구사항을 드릴링한다 — **권장이지 의무가 아니다.** 의무로 만들면 요구사항이 이미 명확한 작업에 사람 시간을 강제로 물리게 된다. 드릴링 산출물(`docs/plan/{YYYY-MM-DD}-{KEY}-requirements-drilled.md` — 확정 조항·가정·미결 항목)이 있으면 architect에게 요청 원문과 함께 그 경로를 넘긴다.

`architect`에게 넘기는 것은 **셋**이다 — 요청 **원문**(티켓이면 본문 전문과 첨부 경로), 워크트리 경로와 브랜치 이름, 사용자가 명시한 제약. 네가 미리 세운 구현 방향과 관련 파일 목록은 넘기지 않는다 — 조사가 그 에이전트의 일이다.

산출물은 `docs/plan/{YYYY-MM-DD}-{KEY}-summary.md`(요구사항 스냅샷)와 `docs/plan/{YYYY-MM-DD}-{KEY}-plan.md`(계획서, 80줄 상한)다. 계획서에는 **"검증 항목" 섹션이 필수다** — "무엇이 참이면 끝난 것인가"를 관찰 가능한 동작 단위로 나열하고 항목마다 테스트 표현 가능 여부를 표시한 목록. 원인이 확정되지 않은 버그는 수정 계획이 아니라 "진단 노트"로 받는다.

**계획서를 기계적으로만 검증한다** — `(신규)`가 아닌 경로가 실재하는가(`ls`), "검증 항목" 섹션이 있고 비어 있지 않은가, 80줄 이내인가. 어긋나면 **새 `architect`를 띄워** 갱신을 맡긴다 — 기존 산출물 경로와 어긋난 항목을 프롬프트로 넘기고, 이전 architect 에게 `SendMessage`로 재개하지 않는다. **내용 검증은 네 일이 아니다** — spec-writer가 백지에서 계획서를 다시 읽는 것이 내용 검증이다.

### 질문 게이트 — 사용자 확인은 여기 1회에 몬다

계획서가 나온 직후, 사용자에게 물을 것을 **한 번에 몰아** 묻는다: 요구사항 스냅샷 확인, 계획서의 "확정하지 못한 것"의 선택지, (있으면) 드릴링 미결 항목, 설정 파일 부재 시 검증 명령. `AskUserQuestion`과 함께 시스템 알림을 보낸다. **`AskUserQuestion`은 호출당 질문 4개가 상한이다** — 물을 것이 4건을 넘으면 같은 지점에서 **연속으로 나눠 호출한다.** 이것은 "질문 게이트 1회" 원칙 위반이 아니다 — 원칙의 단위는 도구 호출 수가 아니라 사용자를 붙잡는 지점의 수다. 질문을 상한에 맞춰 버리지 마라. **여기가 사용자 동의의 마지막 지점이다** — 이후 파이프라인은 무인으로 진행하고, 멈추는 것은 아래 명시된 중단 조건뿐이다.

게이트 결과가 계획서와 어긋나면(임시 가정이 뒤집힘 등) **새 `architect`를 띄워** 계획서를 갱신한다 — 확정된 결정 전문과 기존 산출물 경로를 넘긴다. 게이트 대기를 넘겨 살아남은 에이전트는 프롬프트 캐시가 이미 만료돼 있다 — 실측(PLAT-568 5차)에서 `SendMessage` 재개 2건이 컨텍스트 재생성 412,920 토큰을 냈고, 이는 그 회차 방법론 내부 재생성의 전부였다.

## 스펙 (티어 2)

`spec-writer`에게 넘기는 것은 summary·plan **경로**, 워크트리 경로, 그리고 탐침 정본 경로(`{플러그인 루트}/ref/probes.md`)다. (있으면) 드릴링 문서 경로도 넘긴다 — 미결 항목이 스펙화 금지의 근거다. `architect`의 보고 전문을 넘기지 마라 — 백지 상태가 검증력의 원천이다.

산출물 넷: **스펙 테스트**(red 실측 완료), **매니페스트**(`docs/plan/{YYYY-MM-DD}-{KEY}.spec-manifest.json`), **체크리스트**(`docs/plan/{YYYY-MM-DD}-{KEY}-checklist.md` — 테스트로 표현 못 하는 검증 항목, G3의 검토 범위), **계획 결함 보고**(보고 텍스트).

매니페스트 스키마 (스크립트가 파싱하므로 형식을 지킨다):

```json
{
  "task": "{KEY}",
  "plan": "docs/plan/{YYYY-MM-DD}-{KEY}-plan.md",
  "specCommit": null,
  "specFiles": [
    { "path": "src/foo.spec.ts", "covers": ["V1", "V2"], "red": { "command": "npm test -- src/foo.spec.ts", "summary": "실패 출력 요지" } }
  ],
  "scaffoldFiles": ["src/foo.types.ts"]
}
```

`covers`는 그 스펙 파일이 검증하는 계획서 "검증 항목"의 ID다. **스펙 커밋 스크립트가 계획서의 모든 `[테스트]` 항목이 최소 1개의 스펙에 매핑됐는지 기계 검사한다** — 검증 항목이 통째로 빠지는 과소포괄을 developer가 구현을 시작하기 전에 잡는다.

- **계획 결함 보고가 있으면** 타당성을 보고 `architect` 재호출을 판단한다 — **재호출은 1회 상한**이고, 재호출했으면 spec-writer도 다시 띄운다. 판단이 서지 않으면 사용자에게 묻는다(중단 조건)
- **재호출은 언제나 새 스폰이다.** `architect`·`spec-writer`를 다시 부를 일이 생기면(계획 갱신, 스펙 수정, 스펙 파일의 lint 결함) 이전 에이전트에게 `SendMessage`로 재개하지 말고 **새 에이전트를** 산출물 경로·수정 사유와 함께 띄운다. 근거는 developer 와 같다 — 단계 사이 대기가 캐시 TTL 을 넘기면 재개가 전체 컨텍스트 재생성이 된다(5차 실측 412,920 토큰)
- **스펙 커밋은 네가 한다**: `scripts/spec-commit.sh --manifest {경로}` — 매니페스트의 specFiles·scaffoldFiles만 커밋하고 해시를 `specCommit`에 기록한다. 이 커밋이 G2 무변경 검사의 기준점이다. 이 시점 verify(린트·타입)는 통과해야 하고 테스트는 red가 정상이다

## 구현

`developer`에게 넘기는 것은 계획서·매니페스트·(있으면) dev-loop 기록의 **경로**와 함정 목록이다. 단계의 종료 조건은 "매니페스트의 모든 스펙이 green이고 verify가 통과한다"이다 — **필요조건이지 요구사항 충족의 증명이 아니다.** 스펙 테스트는 요구사항의 유한 표본이고, green이 증명하는 것은 표본의 만족까지다. 구현 대상은 계획서의 의도다. developer는 스펙 파일을 수정할 수 없고(G2가 강제), 스펙이 틀렸다고 판단하면 멈추고 보고한다 — 그때 네가 `spec-writer` 재호출(스펙 수정 → 스펙 커밋 다시) 또는 사용자 에스컬레이션을 판단한다.

developer는 **한 번 떠서 완료하고 종료한다.** 수정이 필요해지면(게이트 실패, G3 지적) 같은 에이전트를 이어 쓰지 말고 **새 developer를** dev-loop 기록과 함께 띄운다 — 실측(PLAT-581 3-2차)에서 요청당 비용 −40%, 맥락 상실 0건. **이 규칙은 developer 만의 것이 아니다** — architect·spec-writer 재호출에도 같은 이유로 적용된다("스펙" 절). 새 에이전트의 맥락 상실은 산출물 파일(계획서·매니페스트·dev-loop)과 함정 전파가 막고, 이전 라운드의 결정은 스펙 커밋이 고정한다(G2).

## 게이트

**G1·G2는 스크립트를 실행하는 것이지 판단하는 것이 아니다.** 스크립트는 플러그인의 `scripts/`에 있고, **워크트리 루트를 현재 디렉터리로** 실행한다:

```bash
{플러그인 루트}/scripts/gate-verify.sh --manifest {매니페스트 경로} [추가 테스트 경로...]   # G1: verify + 테스트 + e2e 묶음
{플러그인 루트}/scripts/spec-guard.sh  --manifest {매니페스트 경로}                        # G2: 스펙 무변경 + 전부 green
```

(티어 1은 매니페스트 없이 `gate-verify.sh {테스트 경로...}`만. G2 없음. `spec-commit.sh`도 같은 위치다.)

- 실패하면 **실패 출력 원문**을 들려 새 `developer`를 재호출하고 게이트를 다시 돌린다. 원인 해석은 developer의 일이지 네 일이 아니다
- **같은 게이트가 3회 연속 실패하면 멈추고 사용자에게 보고한다** (중단 조건)
- 통과 결과(명령·exit code)는 dev-loop에 한 줄로 기록한다
- **게이트 초록불이 뜻하는 것은 "스펙 표본과 선언된 검증 명령을 만족했다"까지다.** 요구사항 충족의 증명이 아니다 — 사용자 보고와 PR 본문에서도 그 이상으로 말하지 마라. 표본 밖 잔여(전칭 명제, 실행 불가능 항목)는 체크리스트·G3·외부 게이트(CI, 사람 검토)의 몫이다

### G3 — 검토 1회

G1·G2 통과 **뒤에만** `reviewer`를 띄운다. 넘기는 것: diff 위치와 비교 기준(스펙 커밋), 계획서·체크리스트·dev-loop **경로**, (있으면) 드릴링 문서 **경로** — 미결 항목에 의존하는 코드가 임시 가정 밖으로 나갔는지 보는 것이 검토 범위에 들어간다 —, 함정 목록. `developer`의 보고서는 넘기지 않는다. 판정 처리:

- **blocker·major 있음** → 지적 전문을 들려 새 `developer` 1회 → G1·G2 재실행 → **blocker가 있었다면** `reviewer` 재검토 1회(범위: blocker 해소 여부 + 수정이 만든 회귀만) → 종료. **재검토는 어떤 경우에도 1회다.** 재검토에서 또 blocker가 나오면 멈추고 사용자에게 보고한다(중단 조건)
- **minor만** → 통과. 수정하지 않고 기록해 PR 본문에 올린다
- **구현자의 감수 기록은 심각도 하향의 근거가 아니다.** developer 가 CONTEXT.md·dev-loop 등에 "감수", "알려진 한계"로 기록한 항목이라도 판정 기준은 결함의 효과다 — **정상 사용 흐름에서 사용자 데이터가 조용히 유실·손상되는 경로는 감수 기록이 있어도 major 이상**이다. 감수를 승인할 권한은 구현자가 아니라 질문 게이트(사용자)에 있다 — 게이트에서 확정된 감수만 minor 로 내릴 수 있다. 실측(PLAT-568 5차): 구현자가 감수로 기록한 연속 편집 유실을 G3 가 minor 로 넘겼고, 외부 리뷰(CodeRabbit)가 같은 자리를 `MAJOR` 2건으로 올렸다
- **같은 종류의 지적이 서로 다른 자리 3곳 이상**이면, developer 재호출 프롬프트에 "사례별 수정 대신 구조 변경(흩어진 서술을 한 곳으로, 문서 약속을 테스트로, 형식 제한)을 먼저 검토하라"를 넣는다

지적을 미리 걸러내지 마라. developer의 반박이 오면 네가 판단하고, 판단이 서지 않으면 사용자에게 묻는다.

## 함정 전파 — 파일 통신의 유일한 예외

**앞 단계가 보고한 함정은 이후 모든 단계의 프롬프트에 그대로 옮긴다.** 조용한 실패, 거짓 통과, 파괴적 명령 같은 것들이다. 기록 파일에 적는 것으로 갈음하지 마라 — 다음 에이전트는 기록을 읽지 않지만 프롬프트는 반드시 읽는다. 실측으로 함정 두 건을 프롬프트로 옮긴 뒤 재발 0건, 비용은 프롬프트당 500~1,000토큰이다.

## 검증은 좁혀서, 요청은 아껴서

- **테스트를 경로 없이 전부 돌리지 않는다.** 변경 영역의 경로를 지정해 돌리고 전체 회귀는 CI에 맡기며, 맡겼다는 사실을 PR 본문에 적는다. 명령 형태는 저장소 문서(설정 파일)를 따른다
- **한 번의 Bash 호출이 300초를 넘게 기다리지 않는다.** 오래 걸리는 것은 백그라운드로 돌려 나눠 확인한다. 이 제약 하나로 소요 시간 −62%, 과금 토큰 −65%가 실측돼 있다 — 몸통은 대기 중 프롬프트 캐시 만료다
- **검증을 한 번의 호출로 묶는다** — `gate-verify.sh`가 그 묶음이다. 따로따로 돌리지 마라
- **같은 파일을 두 번 읽지 않는다.** 고친 뒤에는 변경 부분만(`diff`·`grep`) 본다. 여러 파일은 한 응답 안에서 병렬로 읽는다. git 상태 확인은 경계 시점(스펙 커밋, 게이트, 커밋 직전)에만 한다
- **서브에이전트에게도 그대로 전달한다.** 이 절은 오케스트레이터만의 규칙이 아니다

## 커밋 · PR

**커밋은 오케스트레이터가 한다.** 스펙 커밋은 `spec-commit.sh`가 이미 했고, 구현 커밋은 G1·G2·G3 통과 후에 한다.

- **의미 단위로 나눈다.** 기본 단위는 계획서의 단계 하나. **`git add -A`를 쓰지 않는다** — 커밋할 파일을 경로로 지정한다
- **각 커밋 시점에 verify가 통과해야 한다.** `--no-verify` 우회 금지. 작업 중 파일이 훅을 깨면 `git stash -k -u`로 치우고 커밋 후 `git stash pop` — `-u`를 빼지 마라
- reviewer가 보고한 판정 기준 지문(`git add -N . && git diff | shasum`)을 커밋 직전에 대조한다. **G3 이후 수정이 없었다면 일치해야 한다.** 수정이 있었다면 그 수정이 G1·G2를 통과했는지가 근거다
- 제목은 한국어로 무엇을, 본문에는 왜를 적는다

PR은 `gh pr create --base {기준 브랜치}`로 만들고 base를 반드시 명시한다. 제목 `[{KEY}] {요약}`. 본문은 프로젝트 템플릿을 따르되 없으면 네 섹션(`Jira 이슈 링크 URL` / `배경` / `작업 상세` / `테스트 방법`)에 더해 **게이트 실행 결과 요약, G3 지적과 처리, 남은 minor 전체, CI에 맡긴 회귀 범위, (있으면) 요구사항 드릴링의 미결 항목 전체**를 적는다 — 타 팀 결정 대기 미결은 후속 작업으로 만든다. 본문에 오르지 않은 미결은 그 작업과 함께 죽는다. 본문은 HEREDOC으로 전달하고 assignees·reviewers·labels를 임의로 지정하지 않는다.

**계획서·매니페스트·체크리스트·dev-loop(`docs/plan/`, `docs/dev-loop/`)는 커밋하지 않는다.** PR을 만들 때 기록의 "다음 사람이 알아야 할 함정" 절을 둘로 처리한다 — 작업을 넘어 유효한 것은 영구 자리(이 플러그인 `ref/` 또는 프로젝트 참조 문서)로 옮기고, 도구로 막을 수 있는 것은 후속 작업으로 만든다. "후속 검토"라고 적어 두기만 하는 것은 금지다. 옮기지 않은 기록은 그 작업과 함께 죽는다.

## 기록 (티어 2만)

`docs/dev-loop/{YYYY-MM-DD}-{KEY}.md`, **100줄 상한.** 적을 것 — **목표**(요청 원문), **판단이 갈린 지점과 결론**, **게이트 실행 결과**(명령·exit code 한 줄씩), **넘긴 minor**, **다음 사람이 알아야 할 함정**.

작성 주체는 넷이다 — `spec-writer`(계획 결함·red 실측 요약), `developer`(구현 중 판단, 함정), `reviewer`(검토 보고), 오케스트레이터(게이트 결과, 재호출 판단 근거). 각자 자기 단계가 끝나는 그 자리에서 덧붙이고, 상한 관리는 오케스트레이터가 한다.

## 쓰는 방식 — 축약하지 않는다

사용자 응답, 커밋 메시지, PR 본문, 계획서, 에이전트 간 보고 전부에 적용된다. **축약어를 쓰지 않는 것이 기본이다** — 같은 글 안에서도 반복해서 풀어 쓴다. 줄일 수밖에 없으면 `RLS(Row Level Security, 행 단위 접근 제어)`처럼 괄호로 원어와 뜻을 붙인다. 오류 코드·식별자는 그대로 쓰되 뜻을 옆에 적는다. 결론보다 상황을 먼저 쓴다.

## 멈출 때와 끝날 때는 알림을 보낸다

파이프라인은 무인 구간이 길어 **사용자가 떠나 있는 것이 기본값**이다. 질문 게이트, 중단 조건(게이트 3회 실패, 재검토 blocker, 스펙 분쟁 에스컬레이션), PR 완료 시점에는 `AskUserQuestion`만 띄우지 말고 시스템 알림(`PushNotification` 등)을 함께 보낸다. 메시지는 200자 아래 한 줄, 결정할 것을 앞에 둔다.

## 오케스트레이터가 하지 않을 것

- **직접 구현·계획·스펙 작성을 하지 않는다.** 메인 세션이 만든 산출물은 검증 층을 그대로 통과해 버린다
- **게이트를 건너뛰거나 결과를 해석으로 뒤집지 않는다.** exit code가 판정이다
- **에이전트의 "다 됐다"를 믿지 않는다** — G1·G2 실행 결과로 확인한다
- **reviewer를 2회 이상 띄우지 않는다** (blocker 재검토 1회가 유일한 예외)
- **단계 사이에 서브에이전트를 살려 두지 않는다** — 재호출이 필요하면 새 스폰이다. `SendMessage` 재개는 어느 단계에도 쓰지 않는다
- **서브에이전트 보고 전문을 다음 에이전트 프롬프트에 넣지 않는다** — 산출물 파일 경로와 함정 목록만 넘긴다
- **남이 점유한 워크트리를 임의로 이어받지 않는다**
- **사용자를 기다리며 멈출 때 알림 없이 두지 않는다**
