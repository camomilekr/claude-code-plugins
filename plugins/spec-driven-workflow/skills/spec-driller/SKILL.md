# spec-driller — 요구사항 드릴링

**요구사항 문서를 정본 탐침으로 파헤쳐 모순·엣지케이스·누락을 질문으로 만들고, 사용자의 결정을 받아 문서에 조항으로 기입하는 대화형 스킬이다.** 질문 생성기 + 결정 기록기다 — 그 이상이 아니다.

**답하지 말고 물어라.** "저장이 실패하면 무엇이 보여야 하는가"는 코드에서 도출할 수 없는 **제품 결정**이다. 스킬이 스스로 답을 채우면 이 스킬의 존재 이유가 사라진다 — 가치는 날카로운 질문으로 사람의 판단을 강제로 소환하는 것이고, 답의 정본은 사용자다.

이 스킬은 메인 세션에서 실행한다 — `AskUserQuestion`이 필요하기 때문이다. 요구사항이 크거나 함께 읽을 문서가 많아 컨텍스트가 걱정되면 ①~②(읽기·질문 후보 생성)만 서브에이전트에 위임하고, ③~⑥(선별·질문·기입·보고)은 메인이 직접 한다.

## 언제 쓰는가 / 쓰지 않는가

쓴다:

- **티어 2 작업의 `architect` 호출 전** — 권장이지 의무가 아니다. 요구사항이 이미 명확하면 건너뛴다
- 요구사항이 문서로 확정되지 않았거나, 사용자가 드릴링을 원할 때
- **파이프라인 밖 단독 사용** — 요구사항 문서 보강은 파이프라인 없이도 유용하다. 이 스킬은 파이프라인 상태(매니페스트, 계획서)에 의존하지 않는다

쓰지 않는다:

- 티어 0·1 작업
- 아직 "무엇을 만들 것인가"가 없는 아이디어 단계 — 발산(브레인스토밍류)이 먼저다. 이 스킬은 만들기로 정한 것의 구멍을 찾는 **수렴** 도구라, 발산의 대체가 아니라 후속이다
- 작업 중 요구가 바뀌었을 때의 재실행 관문 — 전체를 재드릴링하지 말고 바뀐 조항만 갱신한다

## 절차

```
입력: 요구사항 — 경로, URL, 티켓 키, 또는 대화 텍스트. 출처를 가리지 않는다
① 읽기    요구사항 + (있으면) 관련 도메인의 CONTEXT.md·기존 스펙을 읽는다
② 드릴링  ref/probes.md의 탐침을 조항마다 적용해 질문 후보를 만든다
③ 선별    "답이 구현을 갈라놓는 질문"만 남긴다
④ 질문    AskUserQuestion으로 몰아서 묻는다 — 상한 8개
⑤ 기입    결정을 확정 조항으로, 보류를 미결 항목으로 문서에 추가한다
⑥ 보고    조항 수·미결 수·가정 수, 한계 명시, 다음 단계 안내
```

### ① 읽기

출처별 도구로 읽는다 — 저장소 마크다운은 `Read`, Jira·Notion은 설치된 조회 수단(스킬·MCP), GitHub 이슈는 `gh issue view`, 대화 텍스트는 그대로. **외부 출처의 원본을 고치러 가지 않는다** — 권한과 동기화 문제는 이 스킬의 범위 밖이고, 산출 문서 머리에 출처 링크를 남기는 것으로 잇는다. 원본 반영이 필요하면 사용자가 한다.

### ② 드릴링 — 탐침은 자유연상이 아니라 정본 목록이다

탐침 정본은 이 플러그인의 `ref/probes.md`다(이 스킬 디렉터리 기준 `../../ref/probes.md`). **반드시 읽고 적용한다.** 질문을 즉흥으로 만들면 회차마다 품질이 흔들리고 발견된 함정이 축적되지 않는다. 같은 목록을 spec-writer가 스펙 레벨에서 자문하므로, 여기서 놓친 것이 아래층에서 한 번 더 걸리는 이중 방어다.

적용 단위: P1(모순)·P5(암묵 가정)는 **문서 전체**에 한 번, 나머지(P2·P3·P4·P6·P7)는 **동작을 정의하는 조항마다** 적용한다. 탐침 수 × 조항 수 전수 매트릭스를 돌리라는 것이 아니다.

### ③ 선별 — 이 스킬의 품질이 여기서 결정된다

**비용은 토큰이 아니라 사람 시간이다.** 질문 수가 늘수록 사용자의 주의력이 흐려진다. 묻는 것은 **답에 따라 계획·스펙·구현이 달라지는 질문**뿐이다. 다음에 해당하면 버린다:

- 답이 무엇이든 구현이 같다
- 코드베이스를 읽으면 알 수 있다 — 읽어서 확인해라, 묻지 마라
- 관례적 기본값이 있고 그걸 벗어날 이유가 없다

탈락한 질문 중 기록할 값어치가 있는 것은 묻지 않고 **"가정: X로 진행"으로 문서에 남겨** 사용자가 훑어볼 수 있게 한다.

단, **기능 범위 자체를 정하는 침묵은 "관례적 기본값"이 아니다.** 종료 조건 유무, 다기기 동기화 여부, 권한 모델처럼 원문이 말하지 않은 것을 범위 밖으로 해석하는 판단은 질문 후보로 남긴다 — 상한에 밀리면 가정이 아니라 **미결**로 기록한다(가정은 훑어보고 지나치기 쉽지만, 미결은 파이프라인이 상속한다).

### ④ 질문 — 한 번에 몰아서

- `AskUserQuestion`으로 묻는다. **각 질문에 선택지를 붙인다**(결정 비용을 낮추기 위해) — 선택지는 제안이지 답이 아니다
- **상한은 8개다**(호출당 최대 4문항 × 연속 2회). 넘치면 P1(모순)과 의무 탐침(P2·P3·P4 — `ref/probes.md`의 구분)에서 나온 질문을 먼저 남기고, 나머지는 가정 또는 미결로 기록한다. 코드베이스가 없는 신규 기능은 "코드베이스를 읽으면 알 수 있다" 기준이 무력해 후보가 부풀기 쉽다 — 같은 우선순위로 자른다. 여러 차례로 나눠 사용자를 반복해서 붙잡지 마라
- 사용자가 결정하지 못한 항목은 **미결**이다. 기본값으로 채우지 마라 — 미결이 명시되어 있으면 spec-writer가 걸러내고 G3가 확인하지만, 조용히 채워진 답은 아무도 다시 보지 않는다
- "지금 결정 유보"를 명시 선택지로 넣지 마라 — 유보가 한 번의 클릭이 되면 결정 회피를 유도한다. 사용자가 기타 입력이나 답변 거부로 보류 의사를 밝히면 그때 미결로 전환하고 결정 주체를 확인한다

### ⑤ 기입 — 산출물은 대화가 아니라 문서 수정이다

파헤친 결과가 세션 대화에만 남으면 architect는 받지 못한다. 완료 조건은 **결정이 문서에 조항으로 기입되고, 각 조항에 결정 근거 한 줄이 남는 것**이다.

- 산출 위치와 이름: **`docs/plan/{YYYY-MM-DD}-{KEY}-requirements-drilled.md`** (`{KEY}`는 Jira 키 또는 브랜치 이름에서 `feature/`를 뗀 부분 — 계획서·매니페스트와 같은 규칙. 둘 다 없으면 짧은 kebab-case 슬러그). 파일명에 "spec"을 쓰지 않는 것은 의도다 — 이 플러그인에서 스펙은 실행 가능한 테스트를 가리키고, 이 문서는 그 위층인 요구사항이다
- `docs/plan/` 아래이므로 계획서와 같은 생애주기다 — 작업 산출물, **커밋 금지**, 값어치 있는 것은 PR 본문으로 이관
- 출처가 저장소 안 마크다운이면 새 파일 대신 그 문서를 직접 보강해도 된다. 티켓 본문·구두 요청처럼 저장소 밖이 출처면 위 규칙의 새 파일로 떨군다
- **원문은 보존하고 섹션을 추가한다.** 원문을 고쳐 쓰면 무엇이 원래 요구이고 무엇이 드릴링의 산물인지 구분이 사라진다

형식:

```markdown
> **드릴링 메타**: spec-driller로 보강됨 · 날짜 `YYYY-MM-DD` · 대상 원문: {출처 경로 또는 링크}

(원문 — 고쳐 쓰지 않고 보존. 저장소 밖 출처면 여기 옮겨 적는다)

## 확정 조항 (spec-driller)

- C-1 {결정된 요구사항 — 코드로 옮길 수 있는 문장으로}
      근거: {사용자 결정 한 줄 — 왜 이 선택인가}

## 가정 (spec-driller — 묻지 않고 진행)

- A-1 가정: {X로 진행} — {관례적 기본값인 이유 한 줄}

## 미결 항목 (spec-driller)

- [ ] UD-1 {질문}
      결정 주체: {사람·팀·절차를 지목한다 — "나중에"는 금지} · 막는 것: {이 답에 의존하는 조항·기능}
      임시 가정: {그 가정으로 진행 가능하면 내용. 불가능하면 "없음 — 이 항목에 의존하는 부분은 착수 보류"}
```

미결 항목의 필수 필드는 넷이다 — **질문**, **결정 주체**, **막는 것**, **임시 가정**. 추적 링크(티켓·스레드)가 있으면 붙인다. 드릴링 시점에는 계획서의 검증 항목이 아직 없으므로 "막는 것"에는 의존하는 조항·기능을 적는다 — 계획서가 생기면 architect가 검증 항목 쪽에 미결 ID를 표기해 링크가 완성된다.

### ⑥ 보고

- 추가된 확정 조항 수, 미결 수, 기록한 가정 수를 보고한다
- **"이 확인은 탐침 목록(`ref/probes.md`)의 범위 안이다"를 명시한다.** 이 스킬은 요구사항 결함을 줄이는 장치이지 없애는 장치가 아니다 — "driller를 통과했으니 요구사항은 완전하다"는 새로운 초록불 착시를 만들지 마라
- "임시 가정 없음 — 착수 보류" 미결이 있으면 `AskUserQuestion`으로 사용자가 정한다: (a) 미결에 의존하지 않는 부분만 범위로 잘라 착수 (b) 전체 보류
- 티어 2 파이프라인으로 이어지면 `architect`에게 요청 원문과 함께 드릴링 문서 경로를 넘긴다

## 미결의 상속 경로 — 파이프라인과 함께 쓸 때

미결이 각 층에서 어떻게 다뤄지는지가 이 형식의 존재 이유다:

| 층 | 미결 처리 |
|---|---|
| `architect` | 미결에 의존하는 검증 항목에 미결 ID(UD-n)를 표기한다 |
| `spec-writer` | **미결에 걸린 항목을 스펙 테스트로 굳히지 않는다.** "임시 가정으로 진행 가능" 항목만 가정을 매니페스트에 명시하고 스펙화한다 |
| G3(`reviewer`) | 미결에 의존하는 코드가 임시 가정 밖으로 나갔는지 본다 |
| PR | 미결 목록을 **PR 본문에 그대로 싣고**, 타 팀 결정 대기 항목은 후속 작업으로 만든다. 본문에 오르지 않은 미결은 그 작업과 함께 죽는다 |

## 금지 — 이 중 하나라도 하면 스킬이 아니라 짐이다

- **미결을 지우거나 기본값으로 채우기.** "일단 이렇게 가정하고 넘어가자"를 사용자 결정 없이 하지 마라
- **원문 고쳐 쓰기.** 확정 조항·가정·미결은 추가 섹션으로만 붙인다
- **"나중에 확인"을 대화에만 남기기.** 같은 후속 조치가 두 번 기록되고 두 번 다 실행되지 않은 실측이 있다 — 문서의 미결 체크리스트가 유일한 자리다
- **외부 원본(Jira·Notion·이슈) 직접 수정.** 산출 문서에 출처 링크를 남기는 것까지가 일이다
- **질문을 여러 차례로 나눠 사용자를 반복해서 붙잡기.** 상한 8개, 몰아서 한 번이다
- **완료 보고에서 "요구사항이 완전해졌다"고 선언하기.** 탐침 목록의 범위 안이라고 말해라

## 합리화 봉쇄 — 스킬 없는 baseline 실측에서 채록된 문장들

같은 요구사항을 스킬 없이 압박(시간 부족·결정권자 부재·"알아서 채워라" 위임) 하에 보강시킨 실측에서, 에이전트는 모순 2건을 질문 없이 해석으로 해소하고 제품 결정 11건을 스스로 내린 뒤 "착수 가능"을 선언했다. 그때 나온 합리화가 아래 왼쪽이다 — **이 문장이 떠오르면 그것이 질문 후보라는 신호다.**

| 합리화 | 실제 |
|---|---|
| "두 조항을 모두 살리는 유일한 구조다" | 모순의 해소는 기술 구조가 아니라 제품 결정이다. "삭제하면 기록도 지운다"가 진짜 의도(예: 개인정보 삭제 요건)일 수 있다 — 어느 조항이 이기는지는 사용자가 정한다 |
| "주류 앱의 표준 UX다" / "그렇게 보는 것이 자연스럽다" | 관례적 기본값은 ③의 **가정 기록** 대상이다. 가정으로 명시해 사용자가 훑어볼 수 있게 남기는 것과, 확정 요구사항으로 못 박는 것은 다르다 |
| "결정권자가 자리에 없다" / "알아서 하라고 위임받았다" | 미결 형식이 정확히 그 상황을 위해 있다. 위임은 결정 주체를 지목할 근거이지 결정의 소멸이 아니다 — "결정 주체: PM · 임시 가정: X로 진행 가능"이 위임의 올바른 기록이다 |
